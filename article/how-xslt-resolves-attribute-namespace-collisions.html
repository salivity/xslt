How XSLT Resolves Attribute Namespace Collisions

This article explains how XSLT processors resolve attribute namespace collisions during XML serialization. It covers the distinctions between expanded QName duplicates and prefix conflicts, the automated "namespace fixup" algorithm, the synthesis of generated prefixes, and the standard rules dictating how processors ensure the output document remains well-formed and compliant with the W3C Namespaces in XML specification.

Expanded QNames and Duplicate Attribute Overwriting

XML elements cannot contain two attributes with the same expanded QName (the combination of a namespace URI and a local name). When an XSLT transformation attempts to add multiple attributes with identical namespace URIs and local names to the same element:

  • Last-Write-Wins Rule: Under the XSLT specification (XSLT 2.0 and later, Section 5.7.1), if two attributes have identical expanded QNames, the processor does not emit both. Instead, the attribute added later in document order or instruction execution replaces the preceding one.
  • Prefix Irrelevance for Identity: The specific prefix used does not matter for this check. If an element receives a:id (where prefix a maps to urn:example:ns) and later b:id (where prefix b maps to urn:example:ns), the processor treats them as the same attribute. The second declaration replaces the first.

Prefix Collisions and Namespace Fixup

A collision also occurs when two attributes use the same prefix to represent different namespace URIs, or when an attribute prefix conflicts with an in-scope element namespace declaration. The XSLT serializer resolves this via namespace fixup:

  1. Conflict Detection: The serializer checks if an attribute’s prefix is already bound to a different namespace URI in the current element scope.
  2. Synthetic Prefix Generation: If a prefix collision is detected, the serializer preserves the attribute's namespace URI by generating an arbitrary, unique prefix (commonly following formats like ns0, ns1, xp_0, or _1).
  3. Prefix Re-declaration: The serializer outputs a namespace declaration attribute (xmlns:generatedPrefix="URI") on the current element and binds the attribute to this newly minted prefix.

For example, if an element already defines xmlns:data="urn:first" and an attribute is written as data:id mapped to urn:second, the serializer changes the attribute output to something like ns0:id and outputs xmlns:ns0="urn:second" on that element.

Unprefixed Attributes and the Default Namespace

In XML, unprefixed attributes never inherit the default namespace (xmlns="...") of their containing element; an unprefixed attribute always resides in no namespace (a null URI).

  • If an attribute is generated with a non-null namespace URI but without a defined prefix, the serializer cannot output it as a plain, unprefixed attribute.
  • The serializer automatically manufactures a new prefix and adds the corresponding namespace declaration to the containing element to ensure the attribute is properly qualified without altering the element’s default namespace.

Preservation of Semantic Equivalence

Throughout the serialization process, XSLT engines prioritize the data model's expanded QNames over lexical representations. Serializers guarantee that:

  • No well-formedness constraints of the XML specification are violated (no duplicate attribute names within a single tag).
  • The association between an attribute's local name and its resolved namespace URI remains identical to the transformation's internal result tree, regardless of whether original prefixes are altered or synthetic prefixes are introduced.
