Using xsl:assert for Data Validation in XSLT 3.0

XSLT 3.0 introduces the <xsl:assert> instruction, providing a built-in mechanism to test conditions and enforce data integrity during transformation execution. This article covers how to configure and define <xsl:assert> elements, customize error reporting, enable assertion checking in processors, and apply these validations to maintain reliable transformation pipelines.

Understanding <xsl:assert>

The <xsl:assert> instruction evaluates a boolean condition specified in its test attribute. If the condition evaluates to true, execution continues unaffected. If the condition evaluates to false, the processor raises a dynamic error (by default, code XTMM9001), signaling that an expected data constraint has been violated.

Basic Syntax and Parameters

The element accepts several attributes to control validation logic and reporting:

  • test: An XPath expression evaluated as an effective boolean value. This is a mandatory attribute.
  • select: An optional XPath expression that generates the error message if the assertion fails.
  • error-code: An optional QName specifying the error code returned upon failure. If omitted, the default err:XTMM9001 is raised.

Alternatively, you can provide the error message using the sequence constructor inside the <xsl:assert> element instead of using the select attribute.

Implementation Example

The following example validates that an incoming invoice contains valid items and positive pricing before processing:

<xsl:template match="invoice">
    <!-- Validate that at least one line item exists -->
    <xsl:assert test="exists(item)" 
                error-code="inv:EMPTY-INVOICE">
        The invoice must contain at least one line item.
    </xsl:assert>

    <xsl:apply-templates select="item"/>
</xsl:template>

<xsl:template match="item">
    <!-- Validate that the item price is a positive number -->
    <xsl:assert test="xs:decimal(price) gt 0" 
                select="concat('Invalid price on item ', @id, ': ', price)"/>

    <processed-item id="{@id}">
        <xsl:value-of select="price"/>
    </processed-item>
</xsl:template>

Enabling Assertions

By default, most XSLT 3.0 processors disable assertions to optimize runtime performance in production environments. To enforce validation, assertion processing must be explicitly activated through processor configuration:

  • Saxon (Command Line): Use the -ea (enable assertions) flag.
  • Saxon (Java API): Call Configuration.setAssertionsEnabled(true) or set the feature FeatureKeys.ASSERTIONS_ENABLED.
  • Configuration Files: Set assertion properties via the respective processor's XML configuration file.

When assertions are disabled, the processor treats <xsl:assert> instructions as no-ops, skipping evaluation entirely and avoiding performance overhead.

<xsl:assert> vs. <xsl:message terminate="yes">

While <xsl:message terminate="yes"> also halts transformation on invalid data, <xsl:assert> provides distinct advantages:

  • Environment Toggle: Assertions can be toggled on during testing and off in production without modifying the stylesheet.
  • Standardized Error Handling: <xsl:assert> consistently generates catchable dynamic errors that integrate cleanly with <xsl:try> and <xsl:catch>.
  • Semantic Intent: Assertions explicitly document preconditions, postconditions, and invariants directly within the transformation logic.
