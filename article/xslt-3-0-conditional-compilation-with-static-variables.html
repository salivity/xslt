XSLT 3.0 Conditional Compilation with Static Variables

In XSLT 3.0, setting the static attribute to "yes" on an <xsl:variable> or <xsl:param> element enables conditional compilation by binding values during the stylesheet compilation phase rather than at runtime. These static variables can be referenced in use-when attributes across the stylesheet, allowing developers to include or exclude templates, functions, imports, and other stylesheet components before the transformation executes. This mechanism provides a native way to handle environment-specific configurations, cross-version compatibility, and debugging logic without runtime performance penalties.

The Static Analysis Phase in XSLT 3.0

XSLT 3.0 distinguishes between two processing phases: the static analysis phase (compile time) and the dynamic evaluation phase (runtime).

Standard XSLT variables are evaluated dynamically; they depend on runtime context, such as source document nodes or dynamic parameters. Consequently, standard variables cannot be used to determine the structure of the compiled stylesheet itself. By defining <xsl:variable name="..." select="..." static="yes"/>, the XSLT processor evaluates the variable's value during static analysis. Because static variables are resolved at compile time, their values must be determinable strictly from static expressions, literals, system properties, or static parameters passed into the processor.

How static Works with use-when

Conditional compilation in XSLT is driven by the use-when attribute, which can be placed on virtually any XSLT element. The expression inside a use-when attribute is evaluated statically during compilation. If the expression evaluates to false(), the XSLT processor strips that element (and its children) from the stylesheet tree entirely, as if it were never written.

Because use-when expressions execute during the static phase, they do not have access to ordinary runtime variables, the context item, or source document data. They can, however, access static variables.

<xsl:stylesheet xmlns:xsl="http://www.w3.org/1999/XSL/Transform" version="3.0">

    <!-- Static variable definition -->
    <xsl:variable name="DEBUG_MODE" select="true()" static="yes"/>

    <!-- Compiled only when DEBUG_MODE is true -->
    <xsl:template match="record" use-when="$DEBUG_MODE">
        <xsl:message>Processing record: <xsl:value-of select="@id"/></xsl:message>
        <xsl:next-match/>
    </xsl:template>

    <!-- Compiled only when DEBUG_MODE is false -->
    <xsl:template match="record" use-when="not($DEBUG_MODE)">
        <xsl:next-match/>
    </xsl:template>

</xsl:stylesheet>

In this example, if $DEBUG_MODE evaluates to false(), the processor completely discards the first template during compilation. No runtime evaluation of the condition takes place during document processing.

Overriding Values with Static Parameters

While static variables provide fixed compilation flags, conditional compilation becomes significantly more versatile when paired with static parameters (<xsl:param static="yes">).

Most XSLT 3.0 processors (such as Saxon) allow users to supply values for static parameters via command-line arguments, API configuration, or build scripts prior to compiling the stylesheet. This enables developers to maintain a single codebase that can be compiled differently depending on target targets:

  • Target Environments: Compiling different base URIs or endpoints for development, staging, or production.
  • Processor Capabilities: Conditionally importing modules based on supported XSLT versions, schema awareness, or vendor extensions using element-available() or function-available().
  • Dead Code Elimination: Omitting heavy diagnostic or legacy fallback templates from production builds to minimize memory consumption and maximize execution speed.

By evaluating expressions before building the execution tree, the static attribute turns <xsl:variable> into a powerful preprocessor directive native to the XSLT 3.0 language.
