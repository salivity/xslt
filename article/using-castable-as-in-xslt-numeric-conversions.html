Using Castable as in XSLT Numeric Conversions

In XSLT 2.0 and later versions, converting raw string data into numeric values is a routine task that carries significant risk of runtime failure. This article explains the role of the castable as operator in XSLT, demonstrating how it prevents fatal transformation errors by testing whether a string conforms to the lexical representation of a numeric type before an explicit conversion is executed.

Preventing Dynamic Runtime Errors

When transforming XML or JSON, source data often contains unexpected, malformed, or missing values—such as empty strings, whitespace, or labels like "N/A". In XPath and XSLT, invoking an explicit type constructor like xs:integer($value) or xs:decimal($value) against an invalid lexical representation causes a fatal dynamic error (FORG0001: Value does not match type). This abruptly halts the entire transformation pipeline.

The primary role of the castable as predicate is defensive validation. It inspects a value and returns a Boolean: true if the value can be successfully transformed into the target atomic type, and false if the conversion would fail.

<xsl:variable name="rawInput" select="'abc'" />

<!-- Safe conversion with a fallback -->
<xsl:variable name="numericValue" 
    select="if ($rawInput castable as xs:decimal) 
            then xs:decimal($rawInput) 
            else 0" />

By placing this check before the explicit constructor, stylesheets remain resilient against dirty data without failing mid-execution.

Lexical Validation vs. Type Checking

It is important to distinguish castable as from instance of.

  • instance of checks the current type of an item in the data model. If a node contains the string '42', ($val instance of xs:integer) evaluates to false because the item is currently an untyped atomic or string value, not an integer.
  • castable as checks the potential for conversion. For that same string '42', ($val castable as xs:integer) evaluates to true because the characters strictly conform to the production rules of the xs:integer lexical space.

Common Implementation Patterns

The castable as operator is typically used in conditional statements, filtering predicates, and sorting keys:

  1. Conditional Assignment: Assigning a default value or () (empty sequence) when a numeric conversion is impossible.

    <xsl:value-of select="if (@price castable as xs:decimal) then xs:decimal(@price) else 0.00" />

  2. Sequence Filtering: Processing only the elements that contain valid numeric strings.

    <xsl:apply-templates select="item[value castable as xs:double]" />

  3. Safe Sorting: Preventing sort failures when nodes expected to be numbers contain arbitrary text.

    <xsl:sort select="if (. castable as xs:integer) then xs:integer(.) else -1" data-type="number" />

Performance and Maintainability

While XSLT 3.0 introduced xsl:try and xsl:catch blocks for exception handling, using castable as remains the preferred, idiomatic approach for data conversion. Catching exceptions incurs computational overhead and results in verbose markup for simple value assignments. Evaluating castable as is lightweight, declarative, and communicates clear intent directly within XPath expressions.
