Handling Invalid Dynamic Attribute Names in XSLT

Dynamic attribute generation in XSLT allows developers to construct attribute names on the fly using runtime values, typically via the <xsl:attribute> instruction or Attribute Value Templates (AVTs). However, XML specifications strictly mandate that all attribute names conform to the rules of an XML Qualified Name (QName) or Non-Colonized Name (NCName). When an expression evaluates to an illegal string—such as one beginning with a number, containing spaces, or incorporating prohibited punctuation—the transformation encounters a conflict between dynamic data and XML grammar rules. This article explains how XSLT handles these runtime name violations across different specification versions and outlines strategies to mitigate transformation failures.

XML Name Constraints

According to the W3C XML specification, an attribute name must be a valid NCName (or QName if prefixed). This means the name must:

  • Start with a letter, underscore (_), or valid non-ASCII start character.
  • Not begin with digits, hyphens (-), or periods (.).
  • Contain only letters, digits, hyphens, underscores, and periods.
  • Contain no whitespace, brackets, slashes, or special symbols (such as $, @, or #).

When <xsl:attribute name="{$dynamicValue}"> is evaluated, the processor must validate the resulting string against these production rules at runtime.

Behavior in XSLT 1.0

In XSLT 1.0, generating an invalid attribute name dynamically is classified as an error:

  • Recoverable vs. Fatal: The 1.0 recommendation states that if the evaluated string is not a QName, it is an error. The specification allows the processor either to signal the error and halt execution or to recover.
  • Recovery Mechanism: If the processor chooses to recover, the behavior is implementation-defined. Most recovering 1.0 processors simply omit the attribute and continue rendering the element, or ignore the faulty instruction entirely.
  • Modern Implementations: Even in 1.0 mode, modern processors (such as libxslt or Saxon) often treat invalid QNames as fatal errors and terminate execution to prevent generating non-well-formed XML output.

Behavior in XSLT 2.0 and XSLT 3.0

The XSLT 2.0 and 3.0 specifications eliminated processor discretion in this scenario, classifying invalid dynamic names as standard non-recoverable dynamic errors.

  • Error Code XTDE0850: If the value of the name attribute in an <xsl:attribute> instruction (or the dynamic name of an <xsl:element>) does not evaluate to a syntactically valid NCName (or QName), the processor must raise dynamic error XTDE0850.
  • Error Code XTDE0860: If the dynamic name contains a prefix that cannot be resolved against the currently in-scope namespace declarations, the processor must raise dynamic error XTDE0860.

Unless explicitly handled, these errors result in an immediate termination of the stylesheet execution.

Processor-Specific Handling

While the specifications define the rules, how errors are surfaced depends on the processor engine:

  • Saxon (Java / .NET / C): Strictly enforces W3C specifications. Saxon halts immediately and outputs a detailed fatal error identifying code XTDE0850, the invalid string, and the line number of the faulty <xsl:attribute> element.
  • Xalan: Commonly used in legacy Java environments. Depending on configuration, Xalan may throw an XSLTProcessorException or log a severe warning while omitting the attribute from the result tree.
  • Microsoft MSXML / .NET XslCompiledTransform: MSXML often throws an XsltException indicating that the attribute name is invalid, immediately aborting the transformation process.

Handling and Preventing Invalid Names

Because dynamic runtime errors cause complete processing failures in modern pipelines, dynamic attribute names should be validated or sanitized prior to generation.

1. Pre-validation and Fallback Logic

Before passing runtime data to the name attribute, verify that the string matches XML naming conventions. In XSLT 2.0 and higher, use the matches() function with an XML NCName regular expression:

<xsl:variable name="rawName" select="dynamic-input" />
<xsl:variable name="isValid" select="matches($rawName, '^[a-zA-Z_][a-zA-Z0-9.\-_]*$')" />

<xsl:choose>
    <xsl:when test="$isValid">
        <xsl:attribute name="{$rawName}">
            <xsl:value-of select="'attribute-value'" />
        </xsl:attribute>
    </xsl:when>
    <xsl:otherwise>
        <!-- Fallback to a default name or skip the attribute -->
        <xsl:attribute name="data-fallback">
            <xsl:value-of select="$rawName" />
        </xsl:attribute>
    </xsl:otherwise>
</xsl:choose>

2. Sanitization

If attribute generation must proceed regardless of source data quality, sanitize the string by replacing illegal characters and ensuring a valid starting character:

  • Prepend a static prefix (e.g., attr_) to prevent leading numbers from causing syntax errors.
  • Use replace() (XSLT 2.0+) or translate() (XSLT 1.0) to strip out whitespace, symbols, and punctuation.

3. Using xsl:try / xsl:catch (XSLT 3.0)

In XSLT 3.0, runtime failures can be trapped dynamically to prevent full pipeline failure:

<xsl:try>
    <xsl:attribute name="{$dynamicValue}">
        <xsl:value-of select="'value'" />
    </xsl:attribute>
    <xsl:catch errors="err:XTDE0850">
        <!-- Gracefully handle the invalid name error -->
        <xsl:attribute name="data-invalid-source-name" select="$dynamicValue" />
    </xsl:catch>
</xsl:try>
