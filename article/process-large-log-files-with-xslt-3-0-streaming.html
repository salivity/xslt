Process Large Log Files with XSLT 3.0 Streaming

Processing multi-gigabyte log files using XSLT 3.0 streaming enables transformations of massive datasets without exhausting system memory. By bypassing the traditional requirement to build an in-memory XML tree, XSLT 3.0 processes nodes sequentially as they arrive from the parser and discards them immediately after execution. This approach eliminates OutOfMemoryError failures, allowing processors to handle arbitrarily large files using a minimal, constant memory footprint.

The Memory Bottleneck of Traditional XSLT

Standard XSLT 1.0 and 2.0 processors require the entire document to be parsed into an in-memory tree—the XQuery and XPath Data Model (XDM). In practice, an XML tree can consume four to ten times the raw file size in RAM. Attempting to parse a 20 GB log file would require up to 200 GB of memory, causing standard processors to crash.

XSLT 3.0 solves this by introducing streaming: the processor reads an input document sequentially, emits output, and immediately releases processed nodes from memory.

Core Mechanisms of XSLT 3.0 Streaming

Streaming relies on specific language constructs designed to enforce sequential, single-pass evaluation.

1. Declaring Streamability

To enable streaming, the stylesheet must explicitly declare a streamable mode using the xsl:mode directive:

<xsl:mode name="stream-log" streamable="yes" on-no-match="shallow-skip"/>

Setting on-no-match="shallow-skip" ensures that the processor skips over large wrapper elements without attempting to retain them in memory, drilling down to the specific log entries.

2. Using copy-of() and snapshot() on Bounded Nodes

Because a streamed node cannot be revisited once passed, expressions cannot freely navigate forward and backward along axes like preceding-sibling:: or following-sibling::.

To process an individual log entry with standard, non-streamed XPath expressions, extract a bounded sub-tree using copy-of() or snapshot():

<xsl:template match="log/entry">
    <!-- Creates an in-memory copy of only this individual entry -->
    <xsl:variable name="currentEntry" select="copy-of(.)"/>
    
    <xsl:if test="$currentEntry/@level = 'ERROR'">
        <error-report timestamp="{$currentEntry/@timestamp}">
            <xsl:value-of select="$currentEntry/message"/>
        </error-report>
    </xsl:if>
</xsl:template>

The memory footprint remains limited to the size of a single <entry> node, regardless of the overall file size.

3. Sequential Iteration with xsl:iterate

For tasks requiring sequence evaluation without deep recursive calls, xsl:iterate replaces standard xsl:for-each. It processes items sequentially, allowing state to be passed from one iteration to the next using parameters:

<xsl:template match="log">
    <xsl:iterate select="entry">
        <xsl:param name="errorCount" select="0"/>
        
        <xsl:choose>
            <xsl:when test="@level = 'ERROR'">
                <xsl:next-iteration>
                    <xsl:with-param name="errorCount" select="$errorCount + 1"/>
                </xsl:next-iteration>
            </xsl:when>
            <xsl:otherwise>
                <xsl:next-iteration>
                    <xsl:with-param name="errorCount" select="$errorCount"/>
                </xsl:next-iteration>
            </xsl:otherwise>
        </xsl:choose>
    </xsl:iterate>
</xsl:template>

4. Maintaining State with Accumulators

Streaming prohibits looking backward to count previous events or retrieve past data. XSLT 3.0 uses xsl:accumulator to maintain state across the stream. Accumulators update values automatically as nodes are encountered:

<xsl:accumulator name="error-counter" 
                 as="xs:integer" 
                 initial-value="0" 
                 streamable="yes">
    <xsl:accumulator-rule match="entry[@level='ERROR']" 
                          select="$value + 1"/>
</xsl:accumulator>

The accumulator value can be queried at any point using accumulator-before() or accumulator-after() without retaining historical elements in memory.

Rules for Maintaining Constant Memory

To ensure a streaming transformation executes in constant memory:

  • Avoid downward navigation after reading: Do not reference child nodes multiple times if they are consumed sequentially. Wrap the context in copy-of() to create a small, transient local tree.
  • Avoid memory-retaining axes: Axes such as following::, preceding::, and unbounded ancestor:: violate streamability constraints.
  • Keep buffers small: Ensure individual repeated elements (e.g., <entry>) remain reasonably sized. A single log entry spanning hundreds of megabytes will still strain heap memory when copied.
