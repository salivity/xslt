Custom Error Codes and Messages in XSLT fn:error

In XSLT 2.0 and later, the standard XPath fn:error() function allows developers to intentionally halt processing and signal dynamic errors. This article explains how to supply custom error codes using XML qualified names (QNames), attach descriptive diagnostic strings, and pass arbitrary context data through the multi-argument signatures of fn:error().

The fn:error() Function Signatures

The XPath and XSLT standard provides four overloaded forms of the fn:error() function:

  1. fn:error(): Raises a generic error without an explicit code or description.
  2. fn:error($code as xs:QName?): Raises an error identified by a specific QName.
  3. fn:error($code as xs:QName?, $description as xs:string): Adds a human-readable diagnostic message.
  4. fn:error($code as xs:QName?, $description as xs:string, $error-object as item()*): Supplies an arbitrary sequence of items (such as elements, attributes, or primitive values) containing diagnostic context.

Defining a Custom Error Code (xs:QName)

Standard error codes belong to the XPath error namespace (http://www.w3.org/2005/xqt-errors). To define a custom error code, assign it to a project-specific namespace. You can generate a QName dynamically using fn:QName() or by casting a prefixed string using xs:QName().

First, bind your custom namespace in your stylesheet:

<xsl:stylesheet version="3.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:xs="http://www.w3.org/2001/XMLSchema"
    xmlns:myerr="http://example.com/ns/errors">

Then create the error code using either method:

<!-- Method A: xs:QName cast with an in-scope prefix -->
fn:error(xs:QName('myerr:INVALID_INPUT'), ...)

<!-- Method B: fn:QName function with explicit URI and local name -->
fn:error(fn:QName('http://example.com/ns/errors', 'INVALID_INPUT'), ...)

Supplying Diagnostic Messages and Objects

The second argument to fn:error() accepts an xs:string, which acts as the human-readable description. The third argument accepts any sequence of items (item()*), allowing you to pass the offending XML node, calculated numbers, or custom structured diagnostic elements.

<xsl:sequence select="
    fn:error(
        xs:QName('myerr:RECORD_NOT_FOUND'),
        concat('Record with ID ', $recordId, ' does not exist.'),
        .
    )"/>

In this call:

  • Code: myerr:RECORD_NOT_FOUND defines the exact error category.
  • Description: A concatenated string explains the failure specifically.
  • Error Object: . (the context item) attaches the node being processed when the failure occurred.

Comprehensive XSLT Example

The following stylesheet validates incoming elements and raises a fully defined error when validation fails:

<?xml version="1.0" encoding="UTF-8"?>
<xsl:stylesheet version="3.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:xs="http://www.w3.org/2001/XMLSchema"
    xmlns:app="http://example.com/app/errors"
    exclude-result-prefixes="xs app">

    <xsl:template match="item">
        <xsl:if test="xs:decimal(@price) lt 0">
            <xsl:sequence select="
                fn:error(
                    xs:QName('app:NEGATIVE_PRICE'),
                    concat('Item ', @id, ' has an invalid negative price of: ', @price),
                    .
                )"/>
        </xsl:if>
        <xsl:copy-of select="."/>
    </xsl:template>

</xsl:stylesheet>

Catching Custom Errors with xsl:try

In XSLT 3.0, errors raised via fn:error() can be caught using xsl:try and xsl:catch. The processor automatically populates specific error variables inside the catch block:

  • $err:code: The xs:QName passed as the first argument.
  • $err:description: The description string passed as the second argument.
  • $err:value: The payload or sequence passed as the third argument.
<xsl:try>
    <xsl:apply-templates select="items/item"/>
    <xsl:catch errors="app:NEGATIVE_PRICE">
        <error-report code="{$err:code}">
            <message><xsl:value-of select="$err:description"/></message>
            <failed-node><xsl:copy-of select="$err:value"/></failed-node>
        </error-report>
    </xsl:catch>
</xsl:try>

Using this structure provides predictable error handling, precise logging, and seamless recovery paths across transformations.
