Using fn:error for Custom Runtime Errors in XSLT

The fn:error() function in XSLT 2.0 and later versions provides a standardized mechanism for intentionally raising dynamic runtime errors during transformation processing. By allowing developers to abort execution or signal controlled failures directly within XPath expressions, it ensures that invalid data or unmet business rules halt the transformation immediately with meaningful, domain-specific diagnostic information rather than silent failures or generic system exceptions.

Function Signatures and Overloads

The fn:error() function belongs to the standard XPath and XQuery Functions and Operators namespace (http://www.w3.org/2005/xpath-functions) and is available in four distinct signatures:

  • fn:error(): Raises a generic error without an explicit code, message, or diagnostic object.
  • fn:error($code as xs:QName?): Raises an error identified by a specific qualified name (QName).
  • fn:error($code as xs:QName?, $description as xs:string): Raises an error with an identifiable QName and a human-readable descriptive string.
  • fn:error($code as xs:QName?, $description as xs:string, $error-object as item()*): Raises an error with a QName, a message, and arbitrary context items (such as problematic XML nodes or values) to assist with debugging.

Raising Errors in XPath Expressions

Before XSLT 2.0, interrupting a stylesheet based on business logic required the <xsl:message terminate="yes"> instruction. While <xsl:message> remains useful for statement-level interruptions, fn:error() can be invoked directly inside any XPath expression, such as variable declarations, sequence constructors, and conditional logic:

<xsl:variable name="customerId" 
              select="if (@id) then xs:string(@id) 
                      else fn:error(xs:QName('my:MissingId'), 'Customer ID is required.')" />

Because fn:error() has an effective return type of none (it never returns a value), it is type-compatible with any expected sequence type in conditional branches.

Structured Error Identification with QNames

Unlike free-form text strings, identifying errors via xs:QName introduces structured, namespace-qualified classification. This practice prevents collision between system-level processor errors and application-level errors:

<xsl:sequence select="if (number(price) gt 0) 
                      then price 
                      else fn:error(QName('http://example.com/errors', 'err:InvalidPrice'), 
                                    'Price must be greater than zero.', 
                                    .)" />

Passing the third argument—the error object (in this case, ., the current node)—preserves context. Advanced processors can output the problematic node within dynamic error traces.

Error Handling in XSLT 3.0

In XSLT 3.0, the role of fn:error() expands from merely terminating execution to working alongside <xsl:try> and <xsl:catch>. A custom error thrown by fn:error() can be intercepted downstream:

<xsl:try>
    <xsl:sequence select="fn:error(xs:QName('app:RecoverableError'), 'Attempting fallback.')" />
    <xsl:catch errors="app:RecoverableError">
        <xsl:value-of select="$err:description" />
    </xsl:catch>
</xsl:try>

When caught, the standard error variables—such as $err:code, $err:description, and $err:value—expose the parameters passed into fn:error(), allowing stylesheets to implement structured exception handling and recovery logic.
