Using empty and exists Functions in XSLT

In XSLT 2.0 and later versions, sequence manipulation is fundamental to data processing, and the built-in XPath functions empty() and exists() serve as the primary tools for sequence inspection. This article covers the purpose, syntax, and operational advantages of empty() and exists(), explaining how they replace older XSLT 1.0 inspection patterns, safeguard against type errors, and improve processing performance through short-circuit evaluation.

Purpose and Signatures

In XPath 2.0 and XSLT 2.0+, all values are sequences. A sequence can contain zero, one, or multiple items consisting of nodes, atomic values, or a mixture of both. The fn:empty() and fn:exists() functions inspect sequence cardinality and return a standard xs:boolean:

  • fn:empty($arg as item()*) as xs:boolean: Returns true if $arg contains zero items (the empty sequence ()); otherwise, returns false.
  • fn:exists($arg as item()*) as xs:boolean: Returns true if $arg contains one or more items; otherwise, returns false.

Logically, exists($seq) is identical to not(empty($seq)).

Replacement of XSLT 1.0 Patterns

In XSLT 1.0, testing whether a node-set contained data typically relied on count() or implicit boolean conversion:

<!-- XSLT 1.0 approach -->
<xsl:if test="count(items/item) > 0">...</xsl:if>
<xsl:if test="items/item">...</xsl:if>

While functional for node-sets, these idioms have critical limitations in XSLT 2.0+:

  1. Performance Overheads with count(): The count() function must evaluate the entire sequence to return its total length. If an XPath expression selects thousands of elements, count() iterates through every single element. In contrast, exists() and empty() can short-circuit: exists() evaluates to true the moment the first item is found, avoiding unnecessary tree traversal.
  2. Effective Boolean Value (EBV) Errors: Directly testing a sequence (e.g., <xsl:if test="$seq">) invokes its Effective Boolean Value. In XPath 2.0+, computing the EBV of a sequence containing more than one atomic value (such as a sequence of strings or integers) raises a fatal runtime error (FORG0006). Using exists($seq) or empty($seq) guarantees safe evaluation regardless of the sequence's contents or data types.

Practical Usage Examples

Testing Element Presence

When checking if child nodes or attributes are present before rendering output:

<xsl:template match="order">
    <xsl:choose>
        <xsl:when test="exists(line-item)">
            <xsl:apply-templates select="line-item" />
        </xsl:when>
        <xsl:otherwise>
            <p>No items found in this order.</p>
        </xsl:otherwise>
    </xsl:choose>
</xsl:template>

Working with Atomic Sequences

When handling sequences produced by functions like tokenize() or sequence constructors:

<xsl:variable name="codes" select="tokenize(@codes, ',\s*')" as="xs:string*" />

<xsl:if test="empty($codes)">
    <xsl:message terminate="yes">Missing required codes attribute.</xsl:message>
</xsl:if>

In this case, evaluating test="$codes" directly would raise an error if multiple tokens exist. Calling empty($codes) reliably checks whether the resulting sequence contains elements.

Summary of Best Practices

  • Use exists($seq) instead of count($seq) > 0 to enable early exit during sequence evaluation.
  • Use empty($seq) instead of count($seq) = 0 or not($seq) when verifying that a sequence contains no items.
  • Always use exists() or empty() when evaluating sequences that may contain atomic values to prevent Effective Boolean Value runtime exceptions.
