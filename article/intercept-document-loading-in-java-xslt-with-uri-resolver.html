Intercept Document Loading in Java XSLT with URIResolver

In Java XSLT processing via the Java API for XML Processing (JAXP), the javax.xml.transform.URIResolver interface provides a mechanism to intercept and customize how external resources are loaded. When an XSLT stylesheet uses constructs like xsl:include, xsl:import, or the XPath document() function, the processor queries a registered URIResolver to obtain the resource. By implementing this interface, developers can redirect URIs, serve documents directly from the Java classpath or memory, apply security boundaries, and implement custom caching strategies.

The Role of URIResolver

By default, an XSLT processor relies on standard networking and filesystem protocols to locate external files referenced in stylesheets. This default behavior fails when resources reside inside packaged JAR files, behind authenticated APIs, or in databases. It also introduces security vulnerabilities, such as Server-Side Request Forgery (SSRF) and XML External Entity (XXE) attacks, if user-supplied stylesheets attempt to read sensitive system files.

A custom URIResolver intercepts these requests before any default network or disk I/O occurs.

The URIResolver Interface

The interface consists of a single method:

public interface URIResolver {
    Source resolve(String href, String base) throws TransformerException;
}
  • href: The target URI string specified in the stylesheet (e.g., <xsl:include href="common.xsl"/> or document('data.xml')).
  • base: The base URI against which relative href values are resolved, typically representing the system ID of the stylesheet or source document that made the call.
  • Return Value: A javax.xml.transform.Source object (such as StreamSource, DOMSource, or SAXSource) containing the resolved resource, or null to instruct the processor to fall back to its default resolution mechanism.

Implementing a Custom URIResolver

To load documents from the application classpath or redirect specific URI schemes, implement the interface and return a StreamSource wrapping the target input stream:

import javax.xml.transform.Source;
import javax.xml.transform.TransformerException;
import javax.xml.transform.URIResolver;
import javax.xml.transform.stream.StreamSource;
import java.io.InputStream;

public class ClasspathURIResolver implements URIResolver {

    @Override
    public Source resolve(String href, String base) throws TransformerException {
        // Intercept custom URI schemes or specific relative paths
        if (href.startsWith("classpath:")) {
            String path = href.substring("classpath:".length());
            InputStream stream = getClass().getClassLoader().getResourceAsStream(path);
            
            if (stream == null) {
                throw new TransformerException("Resource not found on classpath: " + href);
            }
            
            return new StreamSource(stream);
        }

        // Return null to let the default processor resolve other URIs
        return null;
    }
}

Registering the Resolver

A custom resolver can be attached at the factory level (affecting compilation of stylesheets) or at the individual transformer level (affecting runtime document resolution).

1. At the TransformerFactory Level

Setting the resolver on the TransformerFactory intercepts xsl:import and xsl:include elements during stylesheet compilation:

TransformerFactory factory = TransformerFactory.newInstance();
factory.setURIResolver(new ClasspathURIResolver());

Source xsltSource = new StreamSource(new File("main-transform.xsl"));
Templates templates = factory.newTemplates(xsltSource);

2. At the Transformer Level

Setting the resolver on the Transformer instance intercepts runtime calls, such as calls to the document() function during transformation execution:

Transformer transformer = templates.newTransformer();
transformer.setURIResolver(new ClasspathURIResolver());

transformer.transform(new StreamSource(xmlFile), new StreamResult(outputFile));

Common Use Cases

  • Classpath Loading: Allows modular XSLT templates packaged within JAR files to reference one another without requiring absolute filesystem paths.
  • Security Sandboxing: Blocks access to the filesystem (file://) or internal networks (http://) by rejecting unauthorized schemes or unverified hostnames with a TransformerException.
  • Dynamic Generation: Generates XML data dynamically in memory (e.g., using a DOMSource) when requested by the document() function, avoiding intermediary disk writes.
  • Offline Caching: Replaces remote HTTP references with locally cached copies to prevent transformation failures caused by network latency or downtime.
