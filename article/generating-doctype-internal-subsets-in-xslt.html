Generating DOCTYPE Internal Subsets in XSLT

While standard XSLT serialization natively supports external Document Type Declarations (DTDs) through designated serialization attributes, it does not provide a built-in, declarative mechanism for outputting internal DTD subsets. Because the standard <xsl:output> instruction lacks an attribute for internal declarations (such as local entity or element definitions within brackets [...]), developers must employ specific architectural workarounds to serialize XML with an internal subset. These techniques include using character maps, disabling output escaping, switching to plain text serialization, or relying on processor-specific extensions.

The Limitations of Standard <xsl:output>

In XSLT 1.0, 2.0, and 3.0, document type declarations are controlled primarily through the <xsl:output> element using two attributes:

  • doctype-system: Specifies the SYSTEM identifier URI.
  • doctype-public: Specifies the PUBLIC identifier.

When either of these attributes is present, the serializer constructs a standard external DOCTYPE declaration:

<!DOCTYPE root-element SYSTEM "example.dtd">

The W3C XSLT and XQuery Serialization specifications deliberately exclude parameters to construct internal markup declarations (such as <!ENTITY ...> or <!ELEMENT ...>) inside the <!DOCTYPE root [...]> construct. Consequently, achieving an internal subset requires bypassing or modifying the default serialization pipeline.

Workaround 1: Character Maps (XSLT 2.0 and Later)

In XSLT 2.0 and 3.0, the recommended and standard-compliant approach to emit raw markup without triggering escaping is using <xsl:character-map>. This allows designated Unicode characters to be replaced by raw strings during the serialization phase.

<xsl:stylesheet version="2.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform">

    <xsl:output method="xml" use-character-maps="doctype-map"/>

    <xsl:character-map name="doctype-map">
        <xsl:output-character character="&#xE001;" string="&lt;!DOCTYPE root [&#xA;  &lt;!ENTITY sample &quot;value&quot;&gt;&#xA;]&gt;&#xA;"/>
    </xsl:character-map>

    <xsl:template match="/">
        <xsl:value-of select="'&#xE001;'"/>
        <root>
            <!-- Content goes here -->
        </root>
    </xsl:template>

</xsl:stylesheet>

By mapping a private-use character (such as &#xE001;) to the full <!DOCTYPE ... [...]> syntax, the serializer directly writes the declaration before the root element without treating it as invalid XML text nodes.

Workaround 2: Disabling Output Escaping (XSLT 1.0)

In XSLT 1.0, the <xsl:text> element supports the disable-output-escaping="yes" attribute. This instructs the serializer to write literal angle brackets and special characters rather than escaping them as entity references (like &lt; or &gt;).

<xsl:stylesheet version="1.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform">

    <xsl:output method="xml" omit-xml-declaration="no"/>

    <xsl:template match="/">
        <xsl:text disable-output-escaping="yes"><![CDATA[<!DOCTYPE root [
  <!ENTITY test "example">
]>
]]></xsl:text>
        <root>
            <!-- Content goes here -->
        </root>
    </xsl:template>

</xsl:stylesheet>

Note: The W3C specification marks disable-output-escaping as optional, meaning an XSLT processor is not strictly required to support it, especially when piping transformation results directly to another XML pipeline rather than serializing to disk.

Workaround 3: Text Output Serialization

When output escaping mechanisms are unavailable or unsupported, the transformation can switch its serialization method to plain text via <xsl:output method="text"/>. Under this approach, the transformation manually prints every XML component, including the XML prolog, the internal subset, and all element tags. While fully compatible across all processors, this requires the stylesheet to handle all subsequent XML formatting, indentation, and node escaping manually.

Workaround 4: Processor-Specific Extensions

Certain enterprise XSLT engines provide custom extension attributes to handle internal subsets directly. For instance, the Saxon processor family historically offered custom serialization parameters and extension options (such as custom output properties) to hook into the serializer's SAX LexicalHandler, allowing programmatic injection of startDTD, endDTD, and internal entity declarations during transformation execution.
