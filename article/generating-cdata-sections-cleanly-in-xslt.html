Generating CDATA Sections Cleanly in XSLT

Generating <![CDATA[...]]> blocks in XSLT can challenge developers because XSLT processors inherently treat XML input and output as tree structures rather than raw text streams. This article explains the standard, clean method to instruct an XSLT processor to wrap specific element content in CDATA sections using the cdata-section-elements attribute, outlines the dangers of manual string-injection workarounds, and details how to handle edge cases like nested closing brackets.

The Standard Method: cdata-section-elements

The cleanest, standard-compliant way to produce CDATA blocks in XSLT is by configuring serialization through the <xsl:output> directive. You do not need to inject <![CDATA[ and ]]> manually into your template output; the XSLT serializer automatically wraps the text content of specified elements inside CDATA markers upon final emission.

Declare the target element names in the cdata-section-elements attribute of the <xsl:output> declaration at the top level of your stylesheet:

<xsl:stylesheet version="1.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
    <xsl:output method="xml" version="1.0" encoding="UTF-8" indent="yes"
                cdata-section-elements="description script payload"/>

    <xsl:template match="/root">
        <root>
            <description>
                <xsl:value-of select="raw-content"/>
            </description>
        </root>
    </xsl:template>
</xsl:stylesheet>

If raw-content contains reserved XML characters (such as < or &), the serializer automatically emits:

<description><![CDATA[Example with <reserved> & characters]]></description>

Advantages of This Approach

  • Preserves Document Tree Integrity: The XSLT processor maintains a valid DOM/tree structure throughout transformation steps.
  • Portability: Supported by all standard-compliant XSLT 1.0 and 2.0+ processors (e.g., Saxon, Xalan, libxslt).
  • Multiple Elements: You can list multiple space-separated tag names within the attribute.
  • Namespace Support: QNames with prefixes (e.g., cdata-section-elements="my:script") are supported if the namespace is bound in the stylesheet.

Why Avoid disable-output-escaping?

A common anti-pattern involves forcing CDATA markers into the text stream using the disable-output-escaping attribute:

<!-- AVOID THIS PATTERN -->
<xsl:text disable-output-escaping="yes">&lt;![CDATA[</xsl:text>
<xsl:value-of select="raw-content"/>
<xsl:text disable-output-escaping="yes">]]&gt;</xsl:text>

This method introduces several points of failure:

  1. Processor Dependence: The XSLT specification treats disable-output-escaping as optional. Some processors (like certain browser engines or in-memory DOM pipelines) ignore this attribute completely, resulting in literal &lt;![CDATA[ output.
  2. Corrupted Structure: If raw-content contains the character sequence ]]>, the output creates an unescaped, premature closure of the CDATA block, producing invalid XML.
  3. Pipeline Incompatibility: If the output of the XSLT transformation is passed to another in-memory XML handler rather than a text serializer, disable-output-escaping fails because unescaped markup cannot exist as a text node in an XML tree.

Handling the ]]> Sequence in Content

XML strictly forbids the occurrence of ]]> inside a CDATA section. When using cdata-section-elements, compliant XSLT serializers automatically split the text to prevent structural corruption:

<!-- Source content: "A ]]> B" -->
<!-- Standard Serializer Output: -->
<![CDATA[A ]]]]><![CDATA[> B]]>

By allowing the processor to handle serialization via <xsl:output>, character escaping and CDATA boundary safety are managed automatically without extra string-manipulation logic in your templates.
