Using default-mode in Multi-Pass XSLT Stylesheets

In XSLT 3.0, the default-mode attribute provides a cleaner, more modular way to organize multi-pass transformations. Multi-pass processing—where an XML document is transformed through a succession of intermediate stages—traditionally requires adding explicit mode attributes to every template and apply-templates instruction. By declaring default-mode at the stylesheet or package level, developers can assign an entire stylesheet module to a dedicated processing phase, drastically reducing boilerplate code, minimizing mode-mismatch bugs, and improving maintainability.

The Challenge of Multi-Pass Processing in Legacy XSLT

In complex transformations, trying to achieve the desired output in a single pass often leads to overly complicated logic. Breaking the process into multiple discrete steps (such as normalization, structural enrichment, and final serialization) is a standard design pattern.

In XSLT 2.0 and earlier, multi-pass processing relied heavily on modes to separate these stages:

  • Every <xsl:template> rule intended for a specific phase required an explicit mode="phase-name".
  • Every <xsl:apply-templates> instruction within that phase had to specify the same mode.
  • Forgetting a single mode attribute would inadvertently throw the processor back into the default (unnamed) mode, causing hard-to-detect processing bugs.
  • Grouping phase logic into separate files still required manually stamping every template with the same mode identifier.

How default-mode Works

The default-mode attribute, placed on the root <xsl:stylesheet>, <xsl:transform>, or <xsl:package> element, changes the implicit mode for the entire module. Any template rule (<xsl:template match="...">) or processing instruction (<xsl:apply-templates>) that omits an explicit mode attribute automatically assumes the mode defined in default-mode.

<xsl:stylesheet version="3.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:xs="http://www.w3.org/2001/XMLSchema"
    default-mode="normalize">

    <!-- This template automatically belongs to mode="normalize" -->
    <xsl:template match="entry">
        <!-- This apply-templates automatically invokes mode="normalize" -->
        <xsl:apply-templates/>
    </xsl:template>

</xsl:stylesheet>

Architectural Benefits for Multi-Pass Systems

1. File-Level Phase Encapsulation

The most effective pattern for multi-pass XSLT 3.0 is allocating one stylesheet file per pass. A master controller imports each phase, while each individual phase declares its own default-mode:

  • 01-strip-whitespace.xsl sets default-mode="strip".
  • 02-enrich-metadata.xsl sets default-mode="enrich".
  • 03-generate-html.xsl sets default-mode="format".

This isolates each stage conceptually and structurally. Authors can write standard templates without cluttering their code with repetitive mode tags.

2. Prevention of Mode Leaks

When templates accidentally omit a mode attribute in traditional XSLT, they default to the unnamed mode (#unnamed). This can unintentionally capture nodes meant for another stage or cause infinite loops. With default-mode, omission simply means the rule stays within its intended phase context, eliminating common human error.

3. Seamless Integration with the Identity Transform

Multi-pass stages frequently modify only a small subset of nodes while copying the rest unchanged. In XSLT 3.0, combining default-mode with default-mode-on-no-match (or xsl:mode on-no-match="shallow-copy") allows entire passes to act as selective filters with almost zero setup:

<xsl:stylesheet version="3.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    default-mode="enrich">

    <xsl:mode name="enrich" on-no-match="shallow-copy"/>

    <!-- Only specify what changes in this pass -->
    <xsl:template match="price">
        <price currency="USD">
            <xsl:value-of select="."/>
        </price>
    </xsl:template>

</xsl:stylesheet>

4. Clean Orchestration Pipelines

A pipeline orchestrator can pass the results of one phase into variables and apply the next phase sequentially using standard functional idioms or chaining variables:

<xsl:variable name="pass1-result">
    <xsl:apply-templates select="." mode="strip"/>
</xsl:variable>

<xsl:variable name="pass2-result">
    <xsl:apply-templates select="$pass1-result" mode="enrich"/>
</xsl:variable>

<xsl:apply-templates select="$pass2-result" mode="format"/>

Because the individual rules for each pass are self-contained through default-mode, the orchestrator remains easy to read and maintain.
