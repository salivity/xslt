Duplicate Attributes on Elements in XSLT

When generating XML or HTML outputs using XSLT, developers often encounter scenarios where an element receives multiple attributes with identical names. This article explains how the XSLT processor handles duplicate attributes, distinguishing between static stylesheet errors and dynamic attribute generation, detailing the W3C "last-wins" rule, and exploring how namespace-qualified attributes affect this behavior.

Static Duplicate Attributes vs. Dynamic Generation

How an XSLT processor responds to duplicate attributes depends fundamentally on whether the duplication occurs statically within the stylesheet markup or dynamically during transformation processing.

If duplicate attributes appear directly on a literal result element within the XSLT stylesheet (for example, <div class="first" class="second">), the stylesheet itself is not well-formed XML. XML syntax strictly forbids duplicate attribute names on a single element. In this case, the XML parser fails immediately during the initial compilation of the stylesheet before any transformation takes place.

Dynamic Generation and the "Last-Wins" Rule

When attributes are constructed dynamically using the <xsl:attribute> instruction, the XML well-formedness restriction at the stylesheet level no longer applies. Instead, the XSLT specification dictates specific runtime behavior.

According to both the XSLT 1.0 and later (2.0 and 3.0) W3C recommendations, adding an attribute to an element that already contains an attribute with the same expanded name causes the new attribute to replace the previous one. This is commonly referred to as the "last-wins" rule:

<output-element>
    <xsl:attribute name="status">pending</xsl:attribute>
    <xsl:attribute name="status">completed</xsl:attribute>
</output-element>

In the resulting document, <output-element> will have a single attribute: status="completed". The processor evaluates the attributes sequentially, and the later value overwrites the earlier value.

Precedence in Attribute Sets

The last-wins rule also governs how attributes are resolved when using named attribute sets via xsl:use-attribute-sets:

  1. Within an Attribute Set: If an <xsl:attribute-set> contains multiple definitions for the same attribute name, the later definition in stylesheet order takes precedence.
  2. Imported Stylesheets: Attribute definitions in importing stylesheets override definitions from imported stylesheets.
  3. Element-Level Overrides: An explicit <xsl:attribute> child element inside a literal result element always overrides an attribute with the same name originating from an associated xsl:use-attribute-sets declaration, because child <xsl:attribute> instructions are instantiated after the attribute sets are applied.

The Role of Expanded QNames

Attribute duplication in XSLT is evaluated using the expanded QName (Qualified Name), which consists of a local name and a namespace URI, rather than the raw prefix.

  • If two attributes share the same local name and namespace URI, they are duplicates, regardless of whether their prefixes differ (e.g., ns1:id and ns2:id where both prefixes resolve to http://example.com/ns). The latter will replace the former.
  • If two attributes share the same local name but belong to different namespace URIs (or one has a namespace and the other has none), they are treated as distinct attributes. Both will appear in the output document.

Processor Errors and Warnings

While standard XSLT processors overwrite duplicate attributes silently according to specification, some processors can be configured to issue warnings or strict validation errors when duplicate dynamic attributes are generated. Overwriting attributes often signals unintentional design overlap or logic errors in template matching, making logging or detection beneficial during development and debugging.
