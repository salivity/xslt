Eliminate Empty Tags with xsl:where-populated in XSLT 3.0

This article provides a comprehensive overview of the xsl:where-populated instruction in XSLT 3.0, focusing on how it automatically suppresses empty wrapper elements in your output. You will learn the mechanics of how this instruction evaluates content, why it replaces verbose legacy conditional checks, and how to implement it to produce cleaner XML and HTML transformations.

The Problem with Empty Wrapper Elements

In older versions of XSLT (1.0 and 2.0), avoiding empty markup elements—often called "wrapper tags"—was a tedious task. When transforming data where certain fields might be absent, developers typically had to wrap elements in defensive xsl:if tests:

<!-- Verbose Legacy Approach (XSLT 1.0 / 2.0) -->
<xsl:if test="normalize-space(description) != ''">
    <div class="description-container">
        <xsl:value-of select="description"/>
    </div>
</xsl:if>

As the complexity of the child logic grew (such as processing nested loops, multiple child elements, or templates), testing whether the content would actually produce output before generating the outer tag became complex, error-prone, and computationally redundant.

What is xsl:where-populated?

Introduced in XSLT 3.0, xsl:where-populated is an instruction that wraps a sequence constructor. It defers the creation of its enclosing elements until the enclosed instructions have executed. If the result of the instructions produces no meaningful content, the entire output sequence—including outer wrapper elements—is discarded.

Here is the equivalent implementation in XSLT 3.0:

<xsl:where-populated>
    <div class="description-container">
        <xsl:value-of select="description"/>
    </div>
</xsl:where-populated>

If description is missing or contains only whitespace, the entire div is omitted from the result tree automatically.

How XSLT Defines "Populated"

The instruction evaluates whether the generated sequence is "populated" according to specific rules defined in the W3C XSLT 3.0 specification:

  1. Atomic Values: Any atomic value (strings, numbers, booleans) makes the sequence populated, provided it is not an empty string or string containing only whitespace.
  2. Nodes:
    • Element nodes: Automatically considered populated.
    • Text nodes: Considered populated only if they contain at least one non-whitespace character.
    • Comments and Processing Instructions: Considered populated.
    • Document nodes: Evaluated based on whether their children are populated.
  3. Empty Sequences: An empty sequence or a sequence consisting entirely of whitespace text nodes is considered non-populated.

Using xsl:where-populated with Nested Templates

The real strength of xsl:where-populated becomes apparent when dealing with dynamic sub-content, such as xsl:apply-templates. You do not need to predict whether child templates will match or generate nodes:

<xsl:where-populated>
    <section id="metadata">
        <xsl:apply-templates select="author, date, tags"/>
    </section>
</xsl:where-populated>

If none of the selected nodes match active templates, or if all matching templates output nothing, the <section> tag is not created.

Key Benefits

  • Eliminates Redundant Logic: Removes the need to write pre-computation checks or replicate complex XPath expressions inside xsl:if attributes.
  • Improves Maintainability: Keeps markup closely aligned with content logic rather than surrounding it with defensive guards.
  • Optimized Execution: Modern XSLT 3.0 processors (such as Saxon) can optimize the buffering and streaming mechanics of xsl:where-populated more efficiently than manual, deeply nested conditional structures.
