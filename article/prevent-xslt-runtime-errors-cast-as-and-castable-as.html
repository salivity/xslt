Prevent XSLT Runtime Errors: Cast As and Castable As

In XSLT 2.0 and later versions, processing untyped XML input can easily trigger fatal runtime errors when dynamic values fail to match expected data types. Type casting expressions—specifically cast as and castable as—provide developers with the tools to validate and convert atomic values safely before processing them. By using castable as to perform defensive pre-flight checks and cast as to enforce explicit, controlled conversions, stylesheets can gracefully handle malformed, missing, or unexpected data without crashing the transformation pipeline.

The Risk of Runtime Type Errors

XSLT processors frequently encounter values typed as xs:untypedAtomic when reading documents without a strict XML Schema. If a template expects an integer or a date for sorting, arithmetic, or comparison, implicit conversion will occur. If the source data contains invalid text (such as "N/A" inside a <price> element), the processor cannot complete the implicit conversion and halts execution with a dynamic type error (such as FORG0001).

Relying on implicit conversion makes transformations brittle, especially when dealing with external or third-party XML payloads where data hygiene cannot be guaranteed.

Defensive Testing with castable as

The castable as operator tests whether a specific atomic value can be converted into a target schema type without throwing an exception. It evaluates to a boolean: true() if the conversion would succeed, or false() if the value is invalid or cannot be cast to the specified type.

The syntax is:

$value castable as target-type

Because it returns a boolean, castable as functions as a guard condition inside conditional expressions like if (...) then ... else ... or <xsl:if> and <xsl:when> blocks.

For example, testing an incoming date string before treating it as an xs:date:

<xsl:choose>
    <xsl:when test="@published-date castable as xs:date">
        <xsl:value-of select="format-date(xs:date(@published-date), '[B] [D], [Y]')"/>
    </xsl:when>
    <xsl:otherwise>
        <span class="date-unknown">Date unavailable</span>
    </xsl:otherwise>
</xsl:choose>

If @published-date is missing or contains invalid characters, the condition evaluates to false(), bypassing the code that would otherwise cause a fatal runtime crash.

Explicit Conversion with cast as

While constructor functions like xs:integer($val) exist, the cast as expression makes explicit type conversions native to XPath syntax.

The syntax is:

$value cast as target-type

Using cast as eliminates ambiguity. It explicitly documents the intended data type and transforms the value into that target type for subsequent operations. However, using cast as on an incompatible value will still trigger a dynamic error; therefore, it should typically follow a castable as check or be used only when the source schema guarantees compatibility.

The Safe Casting Pattern

The primary method for eliminating dynamic type failures is combining castable as and cast as in an XPath 2.0+ conditional expression. This pattern checks viability first, casts if valid, and provides a safe fallback value if invalid:

if ($input castable as xs:decimal) 
then ($input cast as xs:decimal) 
else 0.0

This pattern guarantees that the resulting value is always an xs:decimal, ensuring that downstream arithmetic operations (such as sum() or division) execute reliably without throwing errors.

Handling Empty Sequences

A common cause of casting failures is the empty sequence (()). By default:

  • () cast as xs:integer throws an error because the target cardinality is exactly one.
  • () castable as xs:integer evaluates to false().

To allow empty sequences to pass through casting operations safely without error, an occurrence indicator (?) can be appended to the type definition:

$input castable as xs:integer?

If $input is empty, this expression evaluates to true(), and $input cast as xs:integer? safely returns an empty sequence rather than halting transformation.
