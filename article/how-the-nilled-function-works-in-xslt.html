How the nilled() Function Works in XSLT

In XSLT 2.0 and later, the nilled() function (fn:nilled()) verifies whether an XML element is explicitly marked as nil according to its associated W3C XML Schema. This article explains how the function operates, its dependence on schema-aware processing, the conditions required for it to return true, and how it differs from a simple attribute check.

Understanding the Function Signature and Return Values

The function is defined in the standard XPath/XSLT functions namespace as:

fn:nilled($arg as node()?) as xs:boolean?

The function evaluates the nilled property of the supplied node according to the XQuery and XPath Data Model (XDM):

  • Returns true: If the argument is an element node that has been schema-validated and determined to be nil.
  • Returns false: If the argument is an element node that is not nilled, or if the document has not undergone schema validation.
  • Returns an empty sequence (()): If the argument is an empty sequence or is not an element node (such as an attribute, text node, or document node).

The Role of Schema Validation and the PSVI

Unlike standard string or attribute matching, nilled() does not simply check for the presence of the literal text xsi:nil="true". Instead, it inspects the Post-Schema-Validation Infoset (PSVI) constructed by a schema-aware XSLT processor (such as Saxon-EE).

For nilled($element) to return true, two distinct criteria must be satisfied during processing:

  1. Schema Definition: The XML Schema definition (.xsd) governing the element must explicitly declare the element with the attribute nillable="true".
  2. Instance Document: The instance XML element must include the attribute xsi:nil="true" (where xsi maps to the standard XML Schema Instance namespace http://www.w3.org/2001/XMLSchema-instance), and the element must contain no child elements or text content that would violate the nilled constraint.

If an element contains xsi:nil="true" but the schema defines nillable="false" (or omits the attribute, defaulting to false), the document is schema-invalid.

Behavior in Non-Schema-Aware Processors

If you execute an XSLT transformation using a basic (non-schema-aware) processor or process an untyped XML document without schema validation:

  • The nilled property of every element node is assigned the default value of false.
  • As a result, nilled($element) returns false, even if the XML source text explicitly contains xsi:nil="true".

When working without schema validation, developers must bypass nilled() and check the attribute directly using XPath:

$element/@*[local-name() = 'nil' and namespace-uri() = 'http://www.w3.org/2001/XMLSchema-instance'] = 'true'

Practical Usage in XSLT

In a schema-aware stylesheet, nilled() is commonly used in template match patterns or conditional statements to handle empty elements that intentionally convey the absence of a value:

<xsl:template match="employee[nilled(salary)]">
    <!-- Handles cases where salary is explicitly nilled by schema rules -->
    <span class="no-data">Salary not disclosed</span>
</xsl:template>

<xsl:template match="employee[not(nilled(salary))]">
    <!-- Handles cases where a valid salary value exists -->
    <span class="data"><xsl:value-of select="salary"/></span>
</xsl:template>

By querying the PSVI directly, nilled() ensures that your transformation logic adheres strictly to the data types and validation constraints established by the underlying XML Schema.
