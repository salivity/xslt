XSLT Parameter Shadowing: Global vs Template Scope

In XSLT, parameter shadowing occurs when a template-level parameter is declared with the exact same name as a top-level global parameter. This article explains the scoping hierarchy of XSLT parameters, how the processor resolves variable name collisions between global and template declarations, and best practices for managing variable scope across different versions of XSLT.

Global vs. Template Parameter Scope

Global parameters are declared using <xsl:param> as direct child elements of the root <xsl:stylesheet> or <xsl:transform> element. These parameters have stylesheet-wide scope, making them accessible to any template, function, or expression throughout the entire document, provided they are not overridden.

Template-level parameters are also declared using <xsl:param>, but as direct children of an <xsl:template> element. Their scope is strictly local to the containing template. They receive values passed explicitly via <xsl:with-param> during template invocation (such as <xsl:apply-templates> or <xsl:call-template>), falling back to a default value defined within the template if no value is passed.

How Shadowing Works

When an <xsl:template> defines an <xsl:param> with a QName (Qualified Name) identical to an existing global <xsl:param>, the template-level parameter shadows the global declaration within the boundary of that template.

  1. Precedence: Within the scope of the template containing the local parameter, any reference to $param-name resolves exclusively to the local parameter. The global parameter is rendered completely inaccessible within that template's execution context.
  2. Isolation: The shadowing effect is strictly confined to the template that declares the local parameter. Outside that template, other templates and global expressions still reference the original global parameter.
  3. No Modification: Shadowing does not alter, reassign, or mutate the global parameter. XSLT is a functional, declarative language; parameters are immutable. Shadowing simply introduces a new, locally scoped binding that hides the outer binding for the duration of the template's execution.

Specification Differences and Validation

Across XSLT 1.0, XSLT 2.0, and XSLT 3.0, the rules regarding global-to-local parameter shadowing remain consistent:

  • Global vs. Local: An XSLT processor will not throw an error when a template parameter shares a name with a global parameter. This is considered valid behavior across all major specifications.
  • Local vs. Local: While a local parameter can shadow a global parameter, XSLT 2.0 and later specifications strictly forbid a local variable or parameter from shadowing another local variable or parameter within an overlapping scope (such as inside nested instructions like <xsl:for-each>). Global-to-local shadowing remains the primary exception where name reuse is permitted across different scoping tiers.

Practical Implications and Best Practices

Because shadowing makes the global parameter unreachable, it can introduce subtle logic errors:

  • Unintended Overrides: If a developer intends to reference a global configuration setting but inadvertently names a template parameter identically, the template will process the local value rather than the global default.
  • Loss of Global Context: If a template genuinely needs access to both a global configuration value and a dynamic template-specific value, the parameters must use distinct names. There is no super or namespace-based syntax to reach an obscured global variable once shadowed by an identically named local variable in the same namespace.
  • Naming Conventions: To prevent accidental collisions, adopt explicit naming conventions. Prefixing global parameters (e.g., $global:setting-name or $g-setting-name) or using descriptive, context-specific names for template arguments helps maintain clarity across complex stylesheets.
