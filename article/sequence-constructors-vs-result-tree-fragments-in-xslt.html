Sequence Constructors vs Result Tree Fragments in XSLT

In XSLT 1.0, storing structured XML content inside a variable produced a result-tree fragment (RTF), an opaque data structure that could not be queried directly using standard XPath expressions without vendor-specific extension functions. XSLT 2.0 resolved this fundamental limitation by introducing sequence constructors, which operate on the XPath and XQuery Data Model (XDM). This shift replaced restrictive tree fragments with first-class sequences of nodes and atomic values, enabling native multi-pass processing, strict typing, and full XPath queryability.

The Limitation of Result-Tree Fragments in XSLT 1.0

In XSLT 1.0, when an <xsl:variable> or <xsl:param> contained a template body rather than a select attribute, the result was a result-tree fragment:

<!-- XSLT 1.0 -->
<xsl:variable name="data">
  <item id="1">Alpha</item>
  <item id="2">Beta</item>
</xsl:variable>

An RTF was essentially an unqueryable tree structure. XSLT 1.0 treated an RTF as a special datatype distinct from a standard node-set:

  • No Path Navigation: You could not apply XPath axes directly to an RTF. Expressions such as $data/item or $data//text() caused a static syntax error.
  • String Conversion Fallback: The only standard operations permitted on an RTF were operations applicable to strings, such as <xsl:value-of select="$data"/> or string($data).
  • Reliance on Extension Functions: To query or iterate over an RTF, developers had to rely on proprietary or EXSLT functions like exsl:node-set($data) to cast the fragment back into a navigable node-set.

How Sequence Constructors Work in XSLT 2.0

XSLT 2.0 completely eliminated the result-tree fragment data type. Instead, template bodies and variable definitions are evaluated as sequence constructors. A sequence constructor is a series of XSLT instructions that generate a sequence of items:

<!-- XSLT 2.0 -->
<xsl:variable name="data" as="element(item)*">
  <item id="1">Alpha</item>
  <item id="2">Beta</item>
</xsl:variable>

A sequence constructor returns an ordered collection of zero or more items conforming to the XDM. These items can be nodes (document, element, attribute, text, comment, processing-instruction) or typed atomic values (such as xs:integer, xs:date, or xs:string).

Key Differences

1. Direct Queryability

Because sequence constructors produce standard XDM sequences, their results remain immediately accessible to XPath 2.0 expressions. You can filter, navigate, and sort the variable's contents without any conversion functions:

<!-- Valid in XSLT 2.0 without extensions -->
<xsl:value-of select="$data[@id = '2']"/>

2. Support for Atomic Values

Result-tree fragments in XSLT 1.0 were restricted to XML nodes rooted in a fragment root. Sequence constructors in XSLT 2.0 can generate sequences containing primitive and atomic values directly:

<xsl:variable name="numbers" as="xs:integer*">
  <xsl:sequence select="(10, 20, 30, 40)"/>
</xsl:variable>

3. Strict Type Safety with the as Attribute

XSLT 2.0 variables allow an as attribute specifying an expected SequenceType. When an as attribute is present, the sequence constructor ensures that the output strictly matches that type, preventing accidental generation of document wrapper nodes:

  • Without as: The variable creates a new document node holding the constructed elements as its children (similar to an RTF, but queryable).
  • With as="element()*": The variable binds directly to the sequence of constructed element nodes without wrapping them in a parent document node.

4. Native Multi-Pass Transformations

Sequence constructors permit multi-pass pipelines inside a single stylesheet. Intermediate transformation stages can be generated into variables, validated, modified, and passed into other templates using standard XPath, eliminating the processing overhead and toolchain dependencies of XSLT 1.0 workarounds.
