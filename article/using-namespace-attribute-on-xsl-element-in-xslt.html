Using namespace Attribute on xsl:element in XSLT

The namespace attribute on the <xsl:element> instruction provides direct, programmatic control over the XML Namespace URI assigned to dynamically generated elements. This article explores how the namespace attribute explicitly binds an element to a target URI, how it interacts with the element's prefix, and how it overrides in-scope namespace declarations to ensure predictable output in XSLT transformations.

Purpose of the namespace Attribute

In XSLT, elements can be constructed using literal result elements or the dynamic <xsl:element> instruction. By default, <xsl:element name="prefix:localName"> resolves the element's namespace URI by looking up the prefix among the in-scope namespace declarations of the stylesheet at that point.

When you specify the namespace attribute, you bypass standard in-scope prefix resolution. The attribute explicitly dictates the exact Namespace URI to which the constructed element belongs:

<xsl:element name="item" namespace="http://example.com/ns/catalog"/>

In this case, the resulting <item> element is bound to http://example.com/ns/catalog, regardless of any default namespaces declared in the stylesheet or the source document.

Prefix and URI Interaction

The name attribute dictates the qualified name (QName) of the element, while the namespace attribute dictates the URI destination. The XSLT processor reconciles them using specific rules:

  1. QName with a Prefix:
    If name="ns:item" and namespace="http://example.com/ns", the processor outputs an element named item tied to http://example.com/ns. It attempts to use the prefix ns. If that prefix is already mapped to a different URI in that scope, the processor generates an alternative prefix or adjusts the declarations to prevent conflicts.

  2. Unprefixed QName:
    If name="item" and namespace="http://example.com/ns", the element belongs to http://example.com/ns. The processor will either emit xmlns="http://example.com/ns" to make it the default namespace or assign a generated prefix (e.g., <xp:item xmlns:xp="http://example.com/ns">).

  3. Empty Namespace:
    If namespace="", the generated element is explicitly placed in no namespace, effectively undeclaring any active default namespace (xmlns="").

Overriding In-Scope Stylesheet Namespaces

A common reason to use the namespace attribute is preventing unwanted namespace inheritance. If a stylesheet defines xmlns:data="http://old-spec.example.com" at the root, generating an element using <xsl:element name="data:record"> would normally inherit that old URI.

Adding the namespace attribute explicitly overrides this behavior:

<xsl:element name="data:record" namespace="http://new-spec.example.com">
  <xsl:value-of select="@id"/>
</xsl:element>

The resulting output associates data:record with http://new-spec.example.com, generating the appropriate xmlns:data="http://new-spec.example.com" declaration in the result tree.

Dynamic URI Assignment with Attribute Value Templates

The namespace attribute accepts Attribute Value Templates (AVTs), allowing namespace URIs to be determined dynamically at runtime based on source data, parameters, or variables:

<xsl:param name="targetNamespace" select="'http://dynamic.example.com/v2'"/>

<xsl:element name="entry" namespace="{$targetNamespace}">
  <xsl:value-of select="title"/>
</xsl:element>

This flexibility allows a single transformation pipeline to route elements to different XML schemas or schema versions based on the content of the input document.
