Public vs Private Functions in XSLT 3.0 Packages

XSLT 3.0 introduced packages as self-contained, reusable modules that encapsulate stylesheet logic and expose explicit interfaces to calling stylesheets. This article explains how XSLT 3.0 packages define their interface boundaries by contrasting public and private visibility declarations on functions, detailing default behaviors, access rules, and practical syntax.

In XSLT 3.0, a package is declared using the top-level <xsl:package> element rather than the traditional <xsl:stylesheet> element. Inside a package, components such as functions, templates, variables, and modes can have their exposure controlled via the visibility attribute.

The visibility Attribute

To manage how functions are consumed outside the package, the <xsl:function> declaration includes the visibility attribute. Its primary values for defining interface boundaries are public and private.

By default, any component declared directly inside an <xsl:package> without an explicit visibility attribute has a visibility of private.

Public Functions (visibility="public")

A function declared with visibility="public" forms part of the package's public interface:

  • External Access: It can be called by any consuming package or stylesheet that imports the module using <xsl:use-package>.
  • Overriding: Consuming packages can override public functions using <xsl:override> if behavioral customization is required.
  • Contract Stability: Public functions serve as the stable contract for external callers, hiding internal implementation details while ensuring interoperability.

Private Functions (visibility="private")

A function declared with visibility="private" represents internal package logic:

  • Encapsulation: It can only be called by other templates and functions defined within the same package (including any stylesheets incorporated via <xsl:include>).
  • Hidden from Consumers: A consuming stylesheet that imports the package via <xsl:use-package> cannot see or invoke a private function. Attempting to call a private function from an external stylesheet results in a static compilation error.
  • Name Protection: Because private functions are completely hidden, their names cannot cause naming conflicts with functions in consuming stylesheets or other imported packages.

Example Implementation

The following example shows a complete package defining both a public interface and a private helper function:

<xsl:package 
    name="urn:example:text-utils"
    package-version="1.0.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:xs="http://www.w3.org/2001/XMLSchema"
    xmlns:utils="urn:example:text-utils"
    exclude-result-prefixes="xs utils"
    version="3.0">

    <!-- Public function: Part of the interface, accessible to callers -->
    <xsl:function name="utils:format-title" as="xs:string" visibility="public">
        <xsl:param name="input" as="xs:string"/>
        <xsl:sequence select="utils:sanitize-whitespace(upper-case($input))"/>
    </xsl:function>

    <!-- Private function: Hidden helper, accessible only inside this package -->
    <xsl:function name="utils:sanitize-whitespace" as="xs:string" visibility="private">
        <xsl:param name="input" as="xs:string"/>
        <xsl:sequence select="normalize-space($input)"/>
    </xsl:function>

</xsl:package>

When a secondary stylesheet loads this package via <xsl:use-package name="urn:example:text-utils" package-version="1.0.0"/>, it can directly invoke utils:format-title(). However, calling utils:sanitize-whitespace() directly from that stylesheet will fail, maintaining strict encapsulation of the internal helper logic.
