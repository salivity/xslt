How to Secure Untrusted User-Supplied XSLT

Allowing untrusted users to supply XSLT stylesheets introduces severe security risks, including Remote Code Execution (RCE), Server-Side Request Forgery (SSRF), local file inclusion, and Denial of Service (DoS). This article outlines the critical security precautions and parser configurations required to neutralize these threats, focusing on disabling dangerous processor capabilities, restricting URI resolution, and isolating execution environments.

Disable Extension Functions and Embedded Scripting

The most critical risk associated with untrusted XSLT is arbitrary code execution through extension functions and embedded scripts. Many XSLT engines, such as .NET's XslCompiledTransform or Java's Xalan and Saxon, historically allow execution of host-language methods (e.g., C# or Java) or scripting blocks (such as msxsl:script).

  • In .NET: Instantiate XsltSettings with EnableScript = false. Never use default settings that permit script blocks.
  • In Java: Enable the Secure Processing feature (XMLConstants.FEATURE_SECURE_PROCESSING) on the TransformerFactory. This automatically blocks calls to arbitrary external Java functions.
  • In PHP/libxslt: Call registerPHPFunctions() only if strictly necessary, and never pass it without limiting it to an explicit, safe whitelist. By default, ensure it is completely disabled.

Block the document() Function

The standard XSLT document() function enables a stylesheet to fetch and parse external XML resources at runtime. Attackers exploit this function to read local files, probe internal networks (SSRF), or leak sensitive tokens.

  • Disable the function entirely: In .NET, set XsltSettings.EnableDocumentFunction = false.
  • Use a custom URI resolver: If the processor cannot disable the function outright, override the default URIResolver (Java) or XmlResolver (.NET). Configure the custom resolver to reject all requests or enforce a strict whitelist that only accepts trusted internal schemas, explicitly denying schemes like file://, gopher://, http://, and https://.

Prevent XML External Entity (XXE) Injection

Because XSLT stylesheets are themselves XML documents, the parser used to read the stylesheet must be secured before the transformation engine ever runs. Unsecured parsers can trigger XXE attacks during the initial parse phase.

  • Completely disable inline Document Type Definitions (DTDs). In Java, set http://apache.org/xml/features/disallow-doctype-decl to true.
  • Disable external general entities (http://xml.org/sax/features/external-general-entities) and external parameter entities (http://xml.org/sax/features/external-parameter-entities).
  • Ensure that the XML input document being transformed is parsed with these exact same anti-XXE constraints.

Enforce Strict Execution Timeouts and Resource Limits

Malicious actors can craft recursive templates or infinite loops inside XSLT stylesheets to consume 100% of the host system's CPU and memory, causing an application-wide Denial of Service.

  • Set a hard timeout on the thread or process executing the transformation. Terminate the transformation immediately if the execution window is exceeded.
  • Enforce limits on output size to prevent memory-exhaustion attacks where a small input generates gigabytes of transformed text.
  • Limit entity expansion depth within the XML parser to mitigate Billion Laughs (XML bomb) attacks.

Isolate the Transformation Environment

Due to the historical frequency of parser vulnerabilities and logic bypasses in complex XSLT engines, defense-in-depth isolation is mandatory.

  • Execute the XSLT transformation worker as a dedicated, low-privilege OS user with no read access to sensitive files or credentials.
  • Run the transformer within a restricted container or ephemeral sandbox.
  • Apply strict egress network firewall rules to the worker container to block all outbound network traffic, mitigating data exfiltration and SSRF even if an attacker manages to invoke external resource loading.
