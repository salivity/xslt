In-Memory Multi-Pass XSLT Transformations

Multi-pass transformations allow developers to break complex XML processing tasks into discrete, sequential steps without writing intermediate files to disk or relying on external pipeline tools. In XSLT 2.0 and later, this is achieved natively in-memory by combining temporary trees stored in variables with distinct transformation modes. This approach simplifies stylesheet maintenance, improves performance, and removes the legacy XSLT 1.0 requirement for vendor-specific node-set() extension functions.

The Foundation: Native Temporary Trees

In XSLT 1.0, storing a transformed XML fragment in a variable produced a Result Tree Fragment (RTF), which could not be navigated with XPath or transformed further without an extension function.

Starting with XSLT 2.0, result tree fragments were replaced by regular document nodes. You can query, navigate, and process any XML structure assigned to an <xsl:variable> just like the original input document, enabling seamless chaining of processing phases directly in system memory.

Structuring the Multi-Pass Pipeline

The standard design pattern for in-memory multi-pass transformation involves three components:

  1. Dedicated Template Modes: Use the mode attribute on <xsl:template> and <xsl:apply-templates> to segregate the logic of each pass.
  2. Intermediate Variables: Capture the output of each pass into an <xsl:variable>.
  3. The Orchestrator Template: A matching template (usually for the root node /) that chains the variables together by feeding the output of one mode as the input to the next.

Step-by-Step Implementation

Consider a scenario where the input XML must first be normalized (e.g., whitespace stripped, elements renamed) in Pass 1, and then aggregated or grouped in Pass 2.

<xsl:stylesheet version="2.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:xs="http://www.w3.org/2001/XMLSchema"
    exclude-result-prefixes="xs">

    <xsl:output method="xml" indent="yes"/>

    <!-- Orchestrator -->
    <xsl:template match="/">
        <!-- Pass 1: Normalize raw input -->
        <xsl:variable name="pass1-result">
            <xsl:apply-templates select="node()" mode="pass1"/>
        </xsl:variable>

        <!-- Pass 2: Calculate and format using Pass 1 results -->
        <xsl:apply-templates select="$pass1-result" mode="pass2"/>
    </xsl:template>

    <!-- Pass 1: Clean and Normalize -->
    <xsl:template match="@* | node()" mode="pass1">
        <xsl:copy>
            <xsl:apply-templates select="@* | node()" mode="pass1"/>
        </xsl:copy>
    </xsl:template>

    <xsl:template match="raw-item" mode="pass1">
        <item status="active">
            <xsl:value-of select="normalize-space(.)"/>
        </item>
    </xsl:template>

    <!-- Pass 2: Final Transformation -->
    <xsl:template match="@* | node()" mode="pass2">
        <xsl:copy>
            <xsl:apply-templates select="@* | node()" mode="pass2"/>
        </xsl:copy>
    </xsl:template>

    <xsl:template match="/*" mode="pass2">
        <catalog>
            <total-items>
                <xsl:value-of select="count(//item[@status='active'])"/>
            </total-items>
            <items>
                <xsl:copy-of select="//item"/>
            </items>
        </catalog>
    </xsl:template>

</xsl:stylesheet>

Chaining Three or More Passes

To extend this pattern to three or more passes, nest additional variables sequentially within the orchestrating template:

<xsl:template match="/">
    <!-- Pass 1 -->
    <xsl:variable name="step1">
        <xsl:apply-templates select="." mode="filter"/>
    </xsl:variable>

    <!-- Pass 2 -->
    <xsl:variable name="step2">
        <xsl:apply-templates select="$step1" mode="enrich"/>
    </xsl:variable>

    <!-- Pass 3 (Final Output) -->
    <xsl:apply-templates select="$step2" mode="format"/>
</xsl:template>

Best Practices

  • Always Specify Modes: Always declare mode attributes on templates designated for a specific stage to prevent templates intended for Pass 2 from accidentally matching during Pass 1.
  • Identity Templates per Mode: When copying unchanged elements from one step to another, declare an identity template specifically for each mode or include a comma-separated list of modes: <xsl:template match="@* | node()" mode="pass1 pass2">.
  • Explicit Variable Typing: In XSLT 3.0, declare the variable type explicitly using as="document-node()" on the intermediate variable to allow early type checking and compiler optimization.
