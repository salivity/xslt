Purpose of static="yes" in XSLT 3.0 Parameters

In XSLT 3.0, declaring a stylesheet parameter with the static="yes" attribute designates it as a static parameter evaluated at compile time rather than during runtime execution. This article explains the technical purpose of static parameters, detailing how they enable conditional compilation, power compile-time configuration through the use-when attribute, and allow XSLT processors to optimize stylesheet execution.

Compile-Time Evaluation

Standard XSLT parameters (static="no", which is the default) are dynamic. They are evaluated at runtime and can depend on the source XML document or runtime context.

When you specify static="yes" on an <xsl:param> element, the XSLT processor evaluates the parameter during stylesheet compilation. The value is fixed before the transformation begins, allowing the stylesheet to behave as if the parameter value were hard-coded into the code.

<xsl:param name="debug-mode" as="xs:boolean" select="false()" static="yes"/>

Because these parameters are resolved at compile time, their values must be supplied prior to compilation by the invoking application or processor API, or they will fall back to their default select expressions.

Enabling Conditional Compilation via use-when

The primary purpose of static parameters is to support conditional compilation. XSLT 3.0 provides the use-when attribute, which can be placed on virtually any XSLT element to conditionally include or exclude that element from the compiled stylesheet.

The expression inside a use-when attribute can only access:

  • System properties
  • Static functions
  • Other static variables and static parameters

Dynamic parameters cannot be referenced within use-when because the compiler cannot evaluate dynamic values while constructing the execution tree.

<xsl:param name="target-environment" as="xs:string" select="'production'" static="yes"/>

<!-- Included only when compiling for development -->
<xsl:template match="order" use-when="$target-environment = 'development'">
    <xsl:message>Processing order: <xsl:value-of select="@id"/></xsl:message>
    <xsl:next-match/>
</xsl:template>

<!-- Standard template used in production -->
<xsl:template match="order" use-when="$target-environment = 'production'">
    <!-- Production transformation logic -->
</xsl:template>

In this scenario, templates or instructions excluded by use-when are completely discarded by the compiler, leaving zero runtime overhead.

Performance Optimization and Dead-Code Elimination

By resolving parameter values statically, XSLT processors can perform advanced optimizations, including:

  • Dead-Code Elimination: Entire branches of code guarded by static parameters (such as logging routines, feature flags, or schema validations) are omitted from the executable package.
  • Constant Folding: Expressions relying on static parameters can be pre-computed at compile time rather than evaluated repeatedly across millions of nodes during execution.
  • Processor Independence: Features requiring specific processor extensions or newer versions can be conditionally compiled so the stylesheet remains backward-compatible without causing compilation errors on older processors.

Restrictions on Static Parameters

To ensure proper compile-time resolution, static parameters must adhere to strict rules:

  • They must be declared as top-level elements (direct children of <xsl:stylesheet> or <xsl:package>).
  • Their select expressions cannot access the dynamic context, meaning they cannot reference source documents, nodes, or dynamic variables.
  • A static parameter can reference other static parameters, provided there are no circular dependencies.
