What is a Saxon Executable File (SEF) in XSLT 3.0?

A Saxon Executable File (SEF) is a compiled, pre-evaluated representation of an XSLT 3.0 stylesheet or XPath expression designed for high-performance execution. This article explains what an SEF file is, why it is used, its primary benefits, and how it fits into the Saxon ecosystem—particularly when executing XSLT transformations in browser or Node.js environments using SaxonJS.

Understanding SEF Files

In standard XSLT workflows, an XSLT processor reads the human-readable XML-based stylesheet, parses its syntax, performs static analysis, builds an abstract syntax tree (AST), optimizes the instructions, and then executes the transformation against the source data.

An SEF file decouples the compilation phase from the execution phase. It stores the optimized internal representation of the stylesheet, effectively functioning as bytecode or an intermediate format. When an application runs an SEF file, the processor can skip the computationally expensive analysis and optimization steps and execute the stylesheet immediately.

Key Benefits of Using SEF

  • Faster Startup and Execution: By performing static analysis ahead of time, runtime startup overhead is virtually eliminated. This makes repeated executions or serverless deployments significantly faster.
  • Client-Side Execution with SaxonJS: The full Saxon compiler is a large, resource-intensive engine traditionally written in Java. Because the compiler cannot efficiently run inside a lightweight web browser, SaxonJS acts purely as an execution engine. It relies entirely on pre-compiled SEF files to run XSLT 3.0 transformations directly within browsers.
  • Code Protection: Distributing an SEF file instead of the original .xsl source protects intellectual property. While not completely encrypted, an SEF file transforms readable XSLT logic into an internal structural model, making reverse-engineering difficult.
  • Early Error Detection: Because compilation occurs ahead of time, static syntax errors, schema-type mismatches, and structural flaws are caught during the build process rather than at runtime.

The SEF Format: XML vs. JSON

Depending on the target environment, SEF files can be serialized into different formats:

  1. JSON Format: Modern implementations targeting JavaScript environments (such as SaxonJS in browsers or Node.js) compile stylesheets into a JSON-based SEF format. Browsers can parse JSON natively at high speeds, minimizing payload processing time.
  2. XML Format: Saxon also supports exporting compiled stylesheets as XML structures, typically used within Java or .NET enterprise environments running Saxon-EE (Enterprise Edition).

How an SEF File is Created and Used

Creating an SEF requires a Saxon processor capable of compiling stylesheets. This is typically done ahead of time using one of two methods:

  • Saxon-EE: The Enterprise Edition of Saxon provides command-line options (such as -export:filename.sef.json or -target:JS) to compile standard XSLT stylesheets into SEF format.
  • The xslt3 NPM Package: A command-line tool built on Node.js that wraps Saxon-EE functionality to compile XSLT 3.0 files directly into JSON-based SEF files without requiring a local Java environment.

Once generated, the SEF file is deployed alongside the runtime engine (such as SaxonJS). The runtime loads the SEF file, binds parameters and source documents, and produces the output document directly.
