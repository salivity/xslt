How XSpec Tests XML Inputs and XSLT Templates

This article explains how the XSpec unit testing framework simulates XML inputs and verifies outputs against Extensible Stylesheet Language Transformations (XSLT) templates. It covers the core test definition elements, how XSpec feeds mock XML contexts to template rules and named templates, and the evaluation mechanisms used to assert structural and boolean expectations.

Setting Up Scenarios and Simulating XML Inputs

XSpec isolates and executes XSLT logic by structuring tests into scenarios using the <x:scenario> element. Within a scenario, input data is defined using the <x:context> element, which acts as the source document or node tree passed to the XSLT processor.

XSpec supports two primary methods for simulating XML input:

  • Inline XML: Developers can embed arbitrary XML fragments directly inside <x:context>. This isolates minimal node trees required to trigger specific templates without needing large mock files.
  • External Documents: By using the href attribute on <x:context> (e.g., <x:context href="sample.xml"/>), XSpec loads external XML files. An optional select attribute can extract a specific sub-tree using an XPath expression.

In addition to the XML payload, <x:context> can specify processing modes via the mode attribute and pass template-level or global parameters using <x:param> child elements.

Invoking Template Rules vs. Named Templates

XSpec mirrors standard XSLT invocation paradigms to trigger the stylesheet's templates:

  1. Rule-Based Execution (Pattern Matching): When <x:context> is supplied alone, XSpec applies templates to the context node, triggering template rules defined by <xsl:template match="...">.
  2. Named Template Invocation: To test named templates (<xsl:template name="...">) directly, XSpec uses the <x:call> element instead of or alongside context data. <x:call template="templateName"> invokes the template directly and can supply parameters via <x:param>.

Asserting Expected Outputs

Once the template processes the simulated input, XSpec captures the result tree fragment or sequence and compares it against assertions defined by <x:expect> elements. XSpec verifies outputs using two main approaches:

Structural Comparison (Deep Equality)

Developers can define an expected XML structure directly inside <x:expect>. XSpec performs a deep comparison between the actual transformed node tree and the expected node tree:

<x:scenario label="when converting a title">
    <x:context>
        <title>Sample Title</title>
    </x:context>
    <x:expect label="it should produce an h1 element">
        <h1>Sample Title</h1>
    </x:expect>
</x:scenario>

During evaluation, XSpec normalizes whitespace based on configuration and verifies node types, element names, namespaces, attributes, and text contents.

XPath Assertions

For scenarios where checking the entire node tree is unnecessary or overly rigid, the test attribute on <x:expect> allows validation via boolean XPath expressions:

<x:expect label="the result must contain three items" 
          test="count(//li) = 3" />

Within the test attribute, the special variable $x:result refers to the actual output returned by the XSLT template, enabling explicit assertions such as $x:result/@status = 'active'.

Under the Hood: The Test Execution Pipeline

XSpec does not evaluate tests through direct interpreter hooks. Instead, it compiles the .xspec test suite into an executable XSLT stylesheet.

This generated stylesheet imports the target XSLT file, wraps the mock data defined in <x:context>, invokes the matching templates or functions, and routes the outputs into comparison logic. The processor (typically Saxon) runs the compiled test stylesheet and outputs an XML or HTML report detailing passed, failed, and pending assertions, alongside visual diffs for structural mismatches.
