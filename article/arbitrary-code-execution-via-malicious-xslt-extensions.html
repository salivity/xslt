Arbitrary Code Execution via Malicious XSLT Extensions

Extensible Stylesheet Language Transformations (XSLT) is a powerful XML-based language used to transform XML documents into readable formats such as HTML, plain text, or other XML structures. While designed for data presentation and restructuring, many XSLT processors support extension functions that interface directly with the underlying host programming language. When an XSLT processor is misconfigured to allow user-supplied stylesheets and has external extensions enabled, an attacker can invoke system-level classes and functions, resulting in critical arbitrary code execution (ACE).

The Role of Extension Functions

Standard XSLT provides built-in functions for string manipulation, basic math, and node-set operations. Because complex business logic occasionally exceeds the native capabilities of XSLT, modern engines provide extension mechanisms. These extensions allow the stylesheet to:

  • Instantiate native objects (such as Java or .NET classes).
  • Execute custom scripts (such as C#, JScript, or VBScript) embedded within the transformation template.
  • Call native framework functions directly through customized XML namespaces.

Under normal development practices, these functions are restricted to pre-compiled, trusted internal libraries. However, when an application blindly evaluates an untrusted or user-controlled XSLT template without hardening the processor, these functions turn into execution primitives for an attacker.

Exploitation Mechanisms Across Platforms

The attack vector depends heavily on the underlying engine and host language. The following implementations highlight how attackers achieve remote code execution through misconfigured processors.

1. Java-Based Processors (Apache Xalan and Saxon)

In Java environments, XSLT engines often support Java language bindings using namespace mappings. If Java reflection or extension calls are not explicitly blocked, an attacker can map a namespace prefix to a standard Java class, such as java.lang.Runtime or java.lang.ProcessBuilder.

<xsl:stylesheet version="1.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform" 
    xmlns:rt="http://xml.apache.org/xalan/java/java.lang.Runtime">
  <xsl:template match="/">
    <xsl:variable name="runtime" select="rt:getRuntime()"/>
    <xsl:variable name="process" select="rt:exec($runtime, 'id')"/>
  </xsl:template>
</xsl:stylesheet>

When the processor parses this stylesheet, it resolves the namespace to the underlying runtime environment, instantiates the class, and calls the specified method with the supplied arguments.

2. .NET Framework (XslCompiledTransform)

In .NET environments, the msxsl:script element allows developers to embed procedural code directly inside the stylesheet. While modern versions of .NET disable this feature by default, developers frequently re-enable it incorrectly using insecure XsltSettings.

<xsl:stylesheet version="1.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform" 
    xmlns:msxsl="urn:schemas-microsoft-com:xslt" 
    xmlns:user="urn:my-scripts">
  <msxsl:script language="C#" implements-prefix="user">
    <![CDATA[
      public string Exec(string cmd) {
          System.Diagnostics.Process.Start(cmd);
          return "";
      }
    ]]>
  </msxsl:script>
  <xsl:template match="/">
    <xsl:value-of select="user:Exec('calc.exe')"/>
  </xsl:template>
</xsl:stylesheet>

If the application initializes the transformer with XsltSettings.TrustedXslt or manually enables EnableScript, the embedded C# code is compiled and executed in the security context of the web application.

3. PHP (libxslt via the XSL Extension)

PHP's XSLTProcessor class allows developers to register global PHP functions using the registerPHPFunctions() method. If this method is called without specifying an allowlist of safe functions, any valid PHP callback can be invoked via the http://php.net/xsl namespace.

<xsl:stylesheet version="1.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform" 
    xmlns:php="http://php.net/xsl">
  <xsl:template match="/">
    <xsl:value-of select="php:function('system', 'whoami')"/>
  </xsl:template>
</xsl:stylesheet>

By leveraging functions like system, passthru, or exec, an attacker executes operating system commands directly.

Root Causes of the Vulnerability

Arbitrary code execution through XSLT extension functions is generally caused by two interconnected flaws:

  1. Processing Untrusted Stylesheets: Applications that accept XSLT templates from untrusted inputs (such as file uploads, user parameters, or unauthenticated API calls) invite attackers to dictate the transformation logic.
  2. Insecure Processor Configuration: Many legacy engines enabled extensions and external entity resolution by default. While modern engines generally disable them out-of-the-box, developers often bypass these security controls to resolve build errors or to support legacy functionality without realizing the exposure.

Prevention and Hardening

To prevent arbitrary code execution, security teams must configure transformation engines securely:

  • Disable External Functions and Scripts: Explicitly configure processors to deny script execution. In Java, configure the XMLConstants.FEATURE_SECURE_PROCESSING attribute and disable external functions (FeatureKeys.ALLOW_EXTERNAL_FUNCTIONS). In .NET, use XsltSettings.Default rather than TrustedXslt.
  • Block Untrusted Stylesheets: Do not allow users to upload or supply custom XSL files. If users need custom views, apply strictly validated XML data against static, server-side stylesheets.
  • Restrict Native Function Mappings: In PHP, restrict registerPHPFunctions() by passing an array containing only the strictly necessary, non-dangerous functions instead of opening all native functions to the parser.
  • Disable External Entity Resolution: Prevent complementary attacks, such as XML External Entity (XXE) injection and Server-Side Request Forgery (SSRF), by disabling the resolution of the document() function and external DTDs.
