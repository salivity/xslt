XSLT Attribute Nodes and Copy Logic Explained

In the XPath and XSLT Data Model (XDM), attributes are treated as first-class nodes rather than secondary key-value metadata attached to element tags. This architectural decision fundamentally dictates how stylesheets select, transform, and replicate data. Because attributes possess node identity, node types, and distinct parent-child relationships, copying them requires adhering to specific tree-construction rules, template matching behaviors, and serialization constraints that differ significantly from simple string-based templating.

Unified Template Matching and Identity Transforms

Because attributes are first-class nodes, they can be matched by pattern rules just like element, text, and comment nodes. This allows XSLT developers to use polymorphic identity templates:

<xsl:template match="@* | node()">
    <xsl:copy>
        <xsl:apply-templates select="@* | node()"/>
    </xsl:copy>
</xsl:template>

In this pattern, the expression @* explicitly selects all attribute nodes of the current context. Treating attributes as nodes allows developers to override the copying logic of a single attribute via <xsl:template match="@target-attribute"> without needing custom conditional branching inside the parent element's template.

Tree Construction Constraints and Temporal Ordering

The most significant impact of first-class attribute nodes on copying logic is the strict lifecycle of element construction. In XSLT, an element node is built sequentially:

  1. The target element node is instantiated.
  2. Attribute nodes are copied or added to the element.
  3. Child nodes (element, text, comment, processing-instruction) are appended.

Because attributes are discrete nodes that belong exclusively to an element's attribute set, an XSLT processor will raise a runtime error (or ignore the operation, depending on the XSLT version and recovery settings) if a stylesheet attempts to copy an attribute node to an element after child content has already been generated. This means all <xsl:copy-of select="@*"/> or <xsl:apply-templates select="@*"/> instructions must execute before any text or child elements are written to the result tree.

Overwrite Semantics Versus Node Appending

When copying multiple child element nodes or text nodes with identical names or content, the result tree appends each node sequentially as siblings. Attributes, however, enforce a uniqueness constraint based on their expanded QName (Namespace URI + Local Name).

When copying attribute nodes:

  • If multiple attribute nodes with the same expanded QName are copied to the same element, the last attribute node processed overwrites any previously copied attributes with that name.
  • Unlike text nodes, which merge or accumulate, attribute node copying represents an atomic replacement of the name-value pair on the target element.

Namespace Binding and Prefix Reconciliation

Attribute nodes maintain an intrinsic association with their namespace URI. When an attribute node is copied to a target element—whether through <xsl:copy> or <xsl:copy-of>—the XSLT processor must copy not only the attribute's local name and string value, but also its namespace node.

If the target element does not already have an in-scope namespace declaration corresponding to the copied attribute's prefix and URI, the processor automatically synthesizes the necessary xmlns:prefix declaration on the enclosing element. This ensures that the attribute node retains its precise semantic identity across different tree contexts.
