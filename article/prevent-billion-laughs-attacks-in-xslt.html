Prevent Billion Laughs Attacks in XSLT

This article outlines how to protect XSLT processors from the Billion Laughs attack, a denial-of-service exploit that abuses XML entity expansion. You will learn the mechanics of the vulnerability within transformation pipelines, the primary defense strategies—such as disabling Document Type Definitions (DTDs) and setting strict entity expansion thresholds—and specific configuration examples across major environments including Java, .NET, and Python.

Understanding the Vulnerability in XSLT

The Billion Laughs attack, or XML entity expansion bomb, relies on recursively defined internal entities inside an inline <!DOCTYPE> declaration. When an XML or XSLT parser attempts to resolve these entities, memory consumption grows exponentially, leading to server crashes or complete denial of service (DoS).

In XSLT pipelines, this vulnerability can be introduced in two distinct places:

  1. The Source XML Document: The input data being transformed contains the malicious DTD payload.
  2. The XSLT Stylesheet: The stylesheet itself is XML and can contain a malicious DTD declaration that expands when parsed by the transformation engine.

Securing XSLT requires hardening both the stylesheet parser and the input document parser.

Core Prevention Strategies

The most effective way to eliminate entity expansion vulnerabilities is to completely disable DTD parsing. If your application does not explicitly require DTDs, disallow them entirely. If DTDs are strictly necessary, you must enforce strict limits on entity expansions.

1. Completely Disallow DTD Processing

Disallowing DOCTYPE declarations entirely removes the vector for both internal entity expansion (Billion Laughs) and external entity injection (XXE). When the parser encounters a <!DOCTYPE> block, it immediately halts and throws an exception.

2. Limit Entity Expansion Thresholds

If legacy requirements prevent completely disabling DTDs, configure entity expansion limits. Most modern parsers provide safety thresholds (often capped at 50,000 to 100,000 expansions by default) that abort processing if an entity expands beyond safe memory bounds.

Parser-Specific Configurations

Java (JAXP, Saxon, and Xalan)

In Java, XSLT operations are handled via TransformerFactory. Apply secure processing features to both the TransformerFactory and the underlying XMLReader used for input parsing.

import javax.xml.XMLConstants;
import javax.xml.transform.TransformerFactory;
import org.xml.sax.XMLReader;
import org.xml.sax.helpers.XMLReaderFactory;

// Configure the TransformerFactory
TransformerFactory factory = TransformerFactory.newInstance();
factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);

// Explicitly disallow DTDs on modern JAXP implementations
factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_STYLESHEET, "");

// Secure the XMLReader used to parse input documents
XMLReader reader = XMLReaderFactory.createXMLReader();
reader.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
reader.setFeature("http://xml.org/sax/features/external-general-entities", false);
reader.setFeature("http://xml.org/sax/features/external-parameter-entities", false);

You can also enforce JVM-level limits via system flags:

  • -Djdk.xml.entityExpansionLimit=1000
  • -Djdk.xml.totalEntitySizeLimit=50000

.NET (XslCompiledTransform)

In .NET, XslCompiledTransform does not parse XML directly; it accepts XmlReader instances. Security depends entirely on how the XmlReaderSettings are configured for both the stylesheet and the source document.

using System.Xml;
using System.Xml.Xsl;

XmlReaderSettings settings = new XmlReaderSettings();
// Prohibit DTD parsing entirely (default in modern .NET)
settings.DtdProcessing = DtdProcessing.Prohibit;
// Ensure external resources are not resolved
settings.XmlResolver = null;

// Read the stylesheet securely
using (XmlReader styleReader = XmlReader.Create("transform.xslt", settings))
{
    XslCompiledTransform xslt = new XslCompiledTransform();
    xslt.Load(styleReader);

    // Read the source document securely
    using (XmlReader inputReader = XmlReader.Create("input.xml", settings))
    using (XmlWriter outputWriter = XmlWriter.Create("output.xml"))
    {
        xslt.Transform(inputReader, outputWriter);
    }
}

Setting DtdProcessing = DtdProcessing.Prohibit throws an XmlException if a <!DOCTYPE> element is encountered. Alternatively, DtdProcessing.Ignore skips the DTD section without throwing an error.

Python (lxml)

lxml relies on libxslt and libxml2. By default, libxml2 has entity expansion limits, but you should explicitly prevent entity resolution to fully mitigate the risk.

from lxml import etree

# Configure a parser that refuses entity expansion and network access
safe_parser = etree.XMLParser(
    resolve_entities=False,  # Prevents expansion of entities
    no_network=True,         # Blocks network access for DTDs
    huge_tree=False          # Enforces libxml2 security limits on tree depth/size
)

# Parse stylesheet and source using the secure parser
xslt_doc = etree.parse("transform.xslt", safe_parser)
transform = etree.XSLT(xslt_doc)

source_doc = etree.parse("input.xml", safe_parser)
result_doc = transform(source_doc)

Never set huge_tree=True when parsing untrusted input in lxml, as that flag disables the internal security limits libxml2 uses to stop entity bombs.

Verification and Testing

To verify your defenses, submit a standard Billion Laughs payload as both the source XML and the XSLT stylesheet in an isolated test environment:

<?xml version="1.0"?>
<!DOCTYPE lolz [
 <!ENTITY lol "lol">
 <!ELEMENT lolz (#PCDATA)>
 <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
 <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">
 <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
]>
<lolz>&lol3;</lolz>

A properly secured configuration will reject this payload instantaneously with an exception regarding disallowed DTD declarations or exceeded entity limits, maintaining stable CPU and memory usage.
