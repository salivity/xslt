Nested XSLT Transformations with fn:transform in XPath

The fn:transform() function, introduced in XPath and XQuery 3.1 and supported natively in XSLT 3.0, enables developers to invoke secondary, nested XSLT transformations dynamically from directly within an XPath expression. By accepting a map of configuration parameters, the function executes an isolated transformation process on specified XML nodes or external resources and returns the results directly to the calling expression as an XDM (XPath Data Model) map. This article explains how fn:transform() operates, how it passes data to nested stylesheets, and how developers can handle the resulting output without relying on external orchestration tools.

Mechanics of the fn:transform() Function

At its core, fn:transform() acts as a self-contained transformation engine embedded inside the host environment. Instead of requiring external tools or build scripts to manage multi-pass transformations, an XSLT stylesheet can invoke another transformation inline.

The function takes a single parameter: an XPath map containing the invocation options. Key entries in this map define the input, the stylesheet to run, and the required runtime parameters:

  • stylesheet-location or stylesheet-node: Specifies the nested stylesheet either by a URI reference or as an in-memory document node (which allows running dynamically generated or embedded stylesheets).
  • source-node or source-text: Supplies the input XML, either as an existing node/tree from the primary transformation context or as serialized XML text.
  • stylesheet-params: A nested map supplying global parameters to the secondary stylesheet.
  • delivery-format: Specifies whether the output should be parsed as raw nodes, serialized text, or saved directly.

Executing a Nested Transformation

When XPath encounters fn:transform(), it suspends the current transformation context to instantiate a new, isolated XSLT processor environment.

A standard invocation looks like this within an XPath expression:

<xsl:variable name="result" select="fn:transform(map{
    'stylesheet-location': 'secondary-transform.xsl',
    'source-node': .,
    'stylesheet-params': map{ xs:QName('mode'): 'strict' }
})"/>

In this pattern:

  1. The current context node (.) is passed cleanly into the nested transformation pipeline via source-node.
  2. The nested processor executes secondary-transform.xsl independently.
  3. The host stylesheet receives an XPath map containing the execution results.

Handling Transformed Output in XPath

Because fn:transform() returns an XPath map, nested transformations integrate seamlessly with standard XPath operations. By default, the output document is stored under the map key output.

Developers can immediately query the transformed nodes using the map lookup operator (?):

<xsl:variable name="filtered-items" select="
    fn:transform(map{
        'stylesheet-location': 'cleanse.xsl',
        'source-node': $raw-data
    })?output//item
"/>

In this example, the nested stylesheet runs, and the subsequent XPath expression (?output//item) immediately navigates the resulting node tree, discarding the rest of the execution metadata.

Advantages of In-XPath Nested Transformations

  • Pipelining without Disk I/O: Intermediate states do not need to be written to the file system or passed through external build scripts; intermediate trees reside completely in memory.
  • Dynamic Stylesheet Generation: A host stylesheet can generate XSLT code on the fly as an XML tree and immediately execute it using the 'stylesheet-node' option.
  • Encapsulation: Complex multi-step document normalizations can be hidden inside specific templates or functions without cluttering the global transformation logic.
