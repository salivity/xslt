Environment Variable Functions in XSLT 3.0

XSLT 3.0 introduced native support for reading the execution environment through the environment-variable() and available-environment-variables() functions. These functions allow stylesheet authors to access operating system settings, server configurations, and system-level parameters directly within transformation code. By providing a standardized interface to host environment properties, XSLT 3.0 simplifies deployment across varied environments and reduces the need for external parameter-injection scripts.

The environment-variable() Function

The environment-variable() function takes a single string argument representing the name of an environment variable and returns its value as an optional string (xs:string?).

environment-variable($name as xs:string) as xs:string?

Its primary purpose is to retrieve external configuration data at runtime. If the specified environment variable exists and the XSLT processor has permission to access it, the function returns its value. If the variable is not defined or the processor restricts access for security reasons, the function returns an empty sequence (()).

Common uses for environment-variable() include:

  • Reading file paths, temporary directories, or deployment paths (e.g., HOME or TMPDIR).
  • Checking the active environment, such as NODE_ENV or STAGE (e.g., differentiating between development, testing, and production).
  • Fetching system-level configurations without needing to pass them explicitly as stylesheet parameters (<xsl:param>).

The available-environment-variables() Function

The available-environment-variables() function takes no arguments and returns a sequence of strings (xs:string*) containing the names of all accessible environment variables.

available-environment-variables() as xs:string*

Its primary purpose is introspection and safe retrieval. Because access to environment variables may vary based on user permissions or XSLT processor settings, this function enables developers to:

  • Verify if a specific variable is exposed before attempting to evaluate it.
  • Enumerate all accessible variables for debugging or dynamic logging during transformations.
  • Implement fallback logic if a critical variable is absent from the host system.

Security and Portability Considerations

Because environment variables can expose sensitive host system information—such as database credentials or API keys—XSLT 3.0 implementations are not required to expose all environment variables. Processors frequently provide configuration flags to disable these functions entirely or restrict access to a curated whitelist.

Additionally, variable name case-sensitivity depends on the underlying operating system and the processor implementation. While names are case-sensitive in Unix-like environments, Windows systems typically treat them as case-insensitive. Relying on available-environment-variables() helps ensure that stylesheets handle these platform-specific variations reliably.
