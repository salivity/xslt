How xsl:vendor-url Identifies XSLT Processors

This article examines how the xsl:vendor-url system property operates as a built-in mechanism for identifying processor origins during Extensible Stylesheet Language Transformations (XSLT). By querying this property through the standard system-property() function, stylesheets can dynamically determine the web address of the organization or open-source project that implemented the active processing engine. This capability enables conditional execution, diagnostic logging, and targeted fallback behavior across heterogeneous execution environments.

The Mechanism of xsl:vendor-url

The W3C XSLT specification mandates three core system properties that every compliant processor must provide: xsl:version, xsl:vendor, and xsl:vendor-url. To access these properties, an XSLT stylesheet evaluates the system-property() XPath function, passing the qualified name of the property as a string argument:

<xsl:value-of select="system-property('xsl:vendor-url')"/>

During transformation, the XSLT runtime intercepts this function call and resolves the QName within the standard XSLT namespace (http://www.w3.org/1999/XSL/Transform). It then returns an implementation-defined string containing the vendor's official URL.

Differentiating Processor Implementations

Each XSLT engine embeds a hardcoded URL that uniquely associates the software with its creator. Common processor outputs include:

  • Saxon: Returns http://www.saxonica.com/ or http://saxon.sf.net/ depending on the release and edition.
  • Apache Xalan: Returns http://xml.apache.org/xalan-j (for Java) or http://xml.apache.org/xalan-c (for C++).
  • libxslt (GNOME): Returns http://xmlsoft.org/XSLT/.
  • MSXML / .NET: Returns http://www.microsoft.com or corresponding developer network resources.

Because processor vendors rarely change their primary web domains, xsl:vendor-url offers a stable identifier that is less prone to minor string formatting discrepancies than the textual descriptions found in xsl:vendor.

Practical Application: Conditional Processing

Developers primarily use xsl:vendor-url to handle proprietary extensions or resolve engine-specific quirks without breaking cross-platform compatibility. By evaluating the vendor URL inside an xsl:choose construct, a stylesheet can execute vendor-specific optimizations when supported while falling back to standard behavior in other environments:

<xsl:choose>
  <xsl:when test="contains(system-property('xsl:vendor-url'), 'saxonica.com')">
    <!-- Saxon-specific logic or extensions -->
  </xsl:when>
  <xsl:when test="contains(system-property('xsl:vendor-url'), 'xmlsoft.org')">
    <!-- libxslt-specific handling -->
  </xsl:when>
  <xsl:otherwise>
    <!-- Portable W3C-compliant fallback -->
  </xsl:otherwise>
</xsl:choose>

Role in Auditing and Diagnostics

In enterprise workflows where transformations pass through multiple pipelines, microservices, or cloud runtimes, transformations may execute under unverified XSLT engines. Embedding xsl:vendor-url into generated metadata, HTML headers, or diagnostic comments allows system administrators to trace output back to the specific engine used at runtime, simplifying debugging when engines interpret edge cases differently.
