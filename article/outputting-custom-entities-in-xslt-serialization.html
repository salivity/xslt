Outputting Custom Entities in XSLT Serialization

Standard XSLT processors face significant architectural hurdles when generating custom entity references such as &custom;. Because XSLT processes an abstracted data model rather than raw markup text, standard serializers are designed to escape ampersands automatically, preventing the native emission of unexpanded, custom entity references without workarounds. This article explains the technical limitations within standard XSLT serializers that prevent direct entity generation, why common workarounds fall short, and how the underlying XML specifications enforce these behaviors.

The XML Data Model Abstraction

The primary limitation stems from the XML Information Set (Infoset) and the XPath and XQuery Data Model (XDM). When an XML document is read into an XSLT processor, the XML parser resolves all general entity references into their replacement text before the XSLT stylesheet operates on the tree. The resulting node tree contains text nodes, not entity references.

Because XSLT operates entirely on this abstract tree, it has no native concept of an "entity reference node." An XSLT processor cannot retain the identity of an incoming entity reference, nor does standard XSLT provide an instruction to create a general entity reference node in the output tree.

Mandatory Serializer Escaping

During the serialization phase—governed by <xsl:output method="xml"/>—the serializer receives text nodes and converts them into characters. According to the W3C serialization specifications:

  • Any literal ampersand (&) within a text node must be escaped as &amp; or a numeric character reference (&#38;).
  • If a stylesheet uses <xsl:text>&amp;custom;</xsl:text>, the serializer outputs &amp;custom;.
  • Literal characters placed into the result tree cannot be selectively shielded from escaping using standard XML node construction.

Consequently, standard serializers do not allow the literal string &custom; to be written directly to the output stream under default XML serialization rules.

Limitations of disable-output-escaping

In XSLT 1.0, the disable-output-escaping="yes" attribute on <xsl:text> or <xsl:value-of> is frequently attempted as a workaround:

<xsl:text disable-output-escaping="yes">&amp;custom;</xsl:text>

While this can force the serializer to output a raw & character, it carries critical limitations:

  • Portability: The XSLT specification designates disable-output-escaping as an optional feature. Processors are not required to support it.
  • Pipeline Failure: It only works when the processor serializes directly to a raw character stream (such as a file or text buffer). If the XSLT transformation outputs to a DOM tree, SAX content handler, or another XML pipeline step, the escaping directive is ignored, and the output reverts to &amp;custom;.
  • Deprecation and Disapproval: The W3C discouraged its use in XSLT 2.0 and 3.0 due to its tendency to produce malformed XML.

Inability to Generate Internal DTD Subsets

For an XML parser to read an output document containing a custom entity like &custom;, the entity must be declared in a Document Type Definition (DTD).

Standard XSLT provides the <xsl:output> element with doctype-system and doctype-public attributes to emit external DTD references:

<xsl:output method="xml" doctype-system="example.dtd"/>

However, standard serializers provide no mechanism to generate an internal DTD subset where custom entities are typically declared (e.g., <!ENTITY custom "value">). Without third-party processor extensions or manual post-processing, standard XSLT cannot output both the custom entity declaration and its corresponding reference in a single, well-formed, valid document.

Character Maps in XSLT 2.0 and 3.0

XSLT 2.0 introduced <xsl:character-map>, which offers a controlled mechanism to replace specific Unicode characters with raw strings during serialization:

<xsl:character-map name="entities">
  <xsl:output-character character="&#xE000;" string="&amp;custom;"/>
</xsl:character-map>

While character maps reliably output the exact string &custom; without relying on disable-output-escaping, limitations remain:

  • They only take effect during actual serialization to a byte or character stream, not during in-memory tree construction.
  • They still do not solve the internal DTD subset declaration problem, meaning the serialized document will fail validation unless an external DTD defines the entity.
