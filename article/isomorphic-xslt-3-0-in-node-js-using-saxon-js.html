Isomorphic XSLT 3.0 in Node.js Using Saxon-JS

This article explores how modern web architectures use Saxon-JS to achieve isomorphic XSLT 3.0 processing across both server-side Node.js environments and client-side web browsers. By leveraging a unified compilation pipeline and the JavaScript-based Saxon-JS runtime, developers can write complex XML transformations once and execute them interchangeably on the server for initial rendering or in the browser for dynamic client-side updates.

The Role of Stylesheet Export Files (SEF)

True isomorphism with Saxon-JS relies on precompiling XSLT 3.0 stylesheets into Stylesheet Export Format (SEF) files. Because the full compilation of an XSLT 3.0 document is computationally heavy and requires enterprise Java tools, Saxon-JS separates compilation from execution. Developers use the Node.js CLI tool xslt3 (backed by Saxon-EE or a native compilation layer) to convert .xsl stylesheets into .sef.json files.

These JSON-based artifacts contain the parsed execution tree of the stylesheet. Because JSON is natively supported by both Node.js and web browsers, the generated SEF file acts as the universal binary that either environment can ingest and execute without needing to re-parse raw XML stylesheet logic.

Server-Side Execution in Node.js

On the server, Node.js uses the saxon-js npm package to process incoming data and render output. By calling the SaxonJS.transform() API, Node.js can perform operations synchronously or asynchronously:

const SaxonJS = require('saxon-js');

const result = SaxonJS.transform({
    stylesheetFileName: 'transform.sef.json',
    sourceFileName: 'input.xml',
    destination: 'serialized'
}, 'sync');

console.log(result.principalResult);

In this context, Node.js often functions as a server-side renderer (SSR) for XML data pipelines. It takes raw XML payloads, applies the SEF transformation, and outputs standard HTML5, JSON, or XML to return directly to the client. This handles first-page loads efficiently, improves Search Engine Optimization (SEO), and hides transformation logic that involves sensitive business rules.

Client-Side Execution in the Browser

The browser environment utilizes the client-targeted build of Saxon-JS, typically loaded via a <script> tag or bundled via frontend tooling. It uses the exact same SaxonJS.transform() API:

SaxonJS.transform({
    stylesheetLocation: 'transform.sef.json',
    sourceLocation: 'dynamic-data.xml',
    destination: 'replaceBody'
}, 'async');

Instead of generating raw strings, the client execution engine can target the Document Object Model (DOM) directly. Saxon-JS supports interactive XSLT (IXSL) extensions, allowing templates to listen for browser events (like clicks or form inputs) and update specific parts of the DOM directly from the XSLT definitions.

Achieving True Isomorphism

Node.js coordinates this isomorphic lifecycle by bridging initial delivery and progressive enhancement:

  1. Shared Logic: The core presentation and business rules remain in a single .xsl file, eliminating duplicate codebases for server rendering and frontend interactivity.
  2. Hybrid Rendering Strategy: Node.js executes the SEF file to deliver a fully populated, accessible HTML page on the initial request. Subsequent client interactions can download the same SEF file, fetch smaller XML or JSON diffs from an API, and apply transformations locally in the user's browser.
  3. Consistent Context: The execution options—including global parameters, initial template modes, and serialization rules—are structurally identical across both Node.js and browser APIs, allowing full reuse of configuration code.

By abstracting away platform-specific execution details behind the SEF runtime, Node.js and Saxon-JS deliver an efficient, unified pipeline for processing enterprise XML across the full web stack.
