How to Use trace() in XSLT 2.0+ for Debugging

This article provides an overview of the trace() function in XSLT 2.0 and later versions, detailing how it helps developers inspect intermediate values during transformation execution. You will learn the syntax of the function, how it operates as a transparent wrapper within XPath expressions, and how to utilize it to output diagnostic data without disrupting the final output of your stylesheets.

The Purpose of the trace() Function

Debugging in declarative languages like XSLT can be challenging because execution order is driven by template matching and expression evaluation rather than procedural steps. The fn:trace() function addresses this by allowing developers to inspect intermediate values in expressions without altering the logic or the generated result of the stylesheet.

Introduced in XPath and XSLT 2.0, fn:trace() acts as an identity function that writes diagnostic information to an external trace log or standard error console as a side effect while returning its input value unchanged.

Function Signature and Parameters

The standard signature for the function defined in the standard XPath Functions namespace is:

fn:trace($value as item()*, $label as xs:string) as item()*

The function takes two arguments:

  1. $value: The item or sequence of items you wish to inspect. This can be a node, an atomic value, a sequence, or any valid XPath expression.
  2. $label: A string label used to identify the output in the diagnostic stream, which helps distinguish between different trace calls in complex stylesheets.

Because the return type matches the input type (item()*), fn:trace() evaluates the first argument, logs both the label and the value, and then returns the evaluated sequence untouched to the calling expression.

Non-Destructive Intermediate Value Inspection

The primary advantage of fn:trace() is that it can wrap any expression without breaking the execution flow. Unlike traditional debugging methods that require inserting temporary elements or modifying template output, trace() can be placed inside:

  • Variable declarations (<xsl:variable>)
  • Sorting keys (<xsl:sort>)
  • Conditional predicates within XPath expressions
  • Function and template parameters

Example: Inspecting an XPath Calculation

Consider a scenario where you calculate a discounted price and need to verify intermediate values inside an XPath expression:

<xsl:value-of select="fn:trace(price * (1 - discount), 'Discounted Total: ')" />

When the processor reaches this instruction, it computes price * (1 - discount), sends the calculated value along with the string "Discounted Total: " to the diagnostic destination, and outputs the resulting number to the result tree just as a standard xsl:value-of would.

Example: Tracking Sequences in Predicates

You can also use trace() inside predicates to observe which nodes are being evaluated:

<xsl:apply-templates select="order[fn:trace(@status = 'shipped', 'Checking Order Status: ')]" />

In this case, the trace log receives a boolean (true or false) for each evaluated order node, allowing you to see exactly how the filter operates at runtime.

Trace Output Destination

The actual format and destination of the output produced by fn:trace() are implementation-defined by the specific XSLT processor being used (such as Saxon or AltovaXML):

  • Standard Error (stderr): Most command-line processors direct the output directly to the system console or standard error stream.
  • Integrated Development Environments (IDEs): Tools like Oxygen XML Editor capture trace messages and display them in a dedicated logging or output pane.
  • Custom Loggers: In programmatic environments (e.g., Java, .NET), processors frequently provide APIs to redirect trace output to application logging frameworks.
