How resolve-QName Resolves Namespaces in XSLT

In XSLT and XPath 2.0 and later, the resolve-QName() function converts a lexical string into an expanded xs:QName by dynamically evaluating it against the in-scope namespaces of a specified element node. This article explores how resolve-QName() operates, its syntax, its role in handling dynamic XML content, and how it manages namespace prefixes and defaults.

Syntax and Parameters

The function signature in standard XPath and XSLT is:

fn:resolve-QName($qname as xs:string?, $element as element()) as xs:QName?
  • $qname: A string representing a lexical QName (e.g., "ns:item" or "item"). If this argument is an empty sequence, the function returns an empty sequence.
  • $element: An element node that provides the context for in-scope namespace declarations.

Mechanism of Namespace Resolution

XML documents define namespace bindings using xmlns and xmlns:prefix declarations, which are inherited hierarchically down the element tree. When an XML document contains qualified names inside attribute values or text content (such as <field type="custom:text"/>), the XSLT processor initially reads those values simply as raw strings, not as semantic XML identifiers.

The resolve-QName() function bridges this gap using the following resolution steps:

  1. Prefix Extraction: It inspects the $qname string to determine if a colon (:) separates a prefix from the local part.
  2. Prefix Lookup: If a prefix is present, the function searches the in-scope namespaces of the provided $element node for a matching prefix binding.
    • If a match is found, the function assigns the associated URI to the resulting xs:QName.
    • If the prefix has no declaration in scope on $element, dynamic error FONS0004 is raised.
  3. Default Namespace Handling: If the $qname string has no prefix, the function assigns the default element namespace (the namespace declared with xmlns="..." on or above $element). If no default namespace is in scope, the resulting xs:QName has no namespace URI.

Practical Application

Consider an XML document where data types are referenced dynamically:

<root xmlns:app="http://example.com/app">
    <data target="app:record" />
</root>

When processing the target attribute, the value "app:record" is a string. In XSLT, you can extract the true namespace URI and local name by resolving it against its parent element:

let $q := resolve-QName(@target, .)
return (
    prefix-from-QName($q),       (: Returns: "app" :)
    local-name-from-QName($q),   (: Returns: "record" :)
    namespace-uri-from-QName($q) (: Returns: "http://example.com/app" :)
)

Error Conditions

  • Invalid Lexical Format (FORG0001): If $qname is not a syntactically valid xs:NCName or xs:QName (e.g., containing invalid characters or multiple colons), an error occurs.
  • Undeclared Prefix (FONS0004): If the prefix parsed from $qname does not exist in the in-scope namespace map of $element, the processor halts with an undeclared namespace error.

By tying string representations directly to an element's in-scope namespace dictionary, resolve-QName() ensures that dynamic element, attribute, and type references retain their accurate semantic meaning across transformations.
