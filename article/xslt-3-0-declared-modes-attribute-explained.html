XSLT 3.0 declared-modes Attribute Explained

This article provides an overview of the declared-modes attribute used within the XSLT 3.0 <xsl:package> element. It explains the attribute's default behavior, its role in enforcing strict validation for template rule modes, and how it helps developers avoid subtle runtime bugs while maintaining modularity and strong encapsulation in large-scale stylesheet development.

In XSLT 3.0, the <xsl:package> element serves as the root container for self-contained, reusable modules of stylesheet code. The declared-modes attribute is an optional setting on <xsl:package> that accepts a boolean value (yes or no), with a default value of yes. Its primary purpose is to specify whether all template modes used within the package must be explicitly defined using top-level <xsl:mode> declarations.

When declared-modes="yes" is in effect, any mode referenced in attributes such as mode on <xsl:template>, <xsl:apply-templates>, or <xsl:next-match> must match a mode explicitly declared via an <xsl:mode name="..."> element within the package or imported from another package. If the XSLT processor encounters a mode name that lacks a corresponding declaration, it raises a static error (XTSE3085).

The main advantage of enforcing declared modes is bug prevention. In legacy XSLT versions, mistyping a mode name—such as writing mode="sumary" instead of mode="summary"—implicitly created a new, empty mode. The processor would silently fall back to built-in template rules without throwing an error, leading to missing output and difficult debugging sessions. Requiring explicit mode declarations ensures that typographical errors are caught at compile time.

In addition to catching typos, declared-modes reinforces the component architecture introduced in XSLT 3.0. Modes in packages can have defined visibility levels, such as public, private, final, or abstract. Because implicit mode generation assigns default visibility and processing behaviors, requiring explicit declarations forces developers to intentionally define the public interface and execution properties—such as on-no-match behavior and streamability—for each mode the package employs.

If a developer sets declared-modes="no", the package behaves similarly to traditional, un-packaged XSLT stylesheets. In this scenario, any undeclared mode referenced in templates is automatically generated with default properties (private visibility and default built-in template rules). While this offers convenience when migrating legacy stylesheets into packages, maintaining the default declared-modes="yes" is considered best practice for robust, production-grade XSLT 3.0 code.
