Using element-available() for XSLT Compatibility

The element-available() function in XSLT allows developers to determine whether a specific instruction or extension element is supported by the executing processor before invoking it. By returning a boolean value, this function enables stylesheets to dynamically adapt to varying XSLT versions (such as 1.0, 2.0, and 3.0) and vendor-specific extension mechanisms. Consequently, it prevents fatal processor errors and ensures cross-platform backward and forward compatibility across heterogeneous runtime environments.

The Challenge of Heterogeneous XSLT Environments

Enterprise systems and web applications often deploy stylesheets across disparate processors, including libxslt, Apache Xalan, and modern Saxon engines. When a stylesheet relies on features introduced in newer specifications (such as xsl:analyze-string from XSLT 2.0) or vendor-specific proprietary extensions, older or minimal processors typically encounter unknown instruction elements. In normal execution, encountering an unrecognized instruction element triggers a fatal static error, terminating the transformation entirely.

Dynamic Capability Detection

The element-available() function resolves this issue by inspecting the processor's element registry at runtime or compile time. It takes a single string argument—the qualified name (QName) of an element—and evaluates whether the processor can execute it as an instruction:

<xsl:choose>
    <xsl:when test="element-available('xsl:analyze-string')">
        <!-- Advanced regex processing for XSLT 2.0+ engines -->
    </xsl:when>
    <xsl:otherwise>
        <!-- Fallback baseline logic for XSLT 1.0 processors -->
    </xsl:otherwise>
</xsl:choose>

By querying element support inside conditional blocks (xsl:if or xsl:choose), the stylesheet establishes branch logic. The processor ignores instructions enclosed within branches that evaluate to false, allowing newer features to be leveraged when available while maintaining uninterrupted execution on legacy engines.

Coexistence with xsl:fallback and Forwards-Compatible Mode

The element-available() function frequently complements XSLT's native forwards-compatible behavior and the <xsl:fallback> element. When a stylesheet specifies a version higher than what the active engine supports (for instance, a version="2.0" stylesheet running on a 1.0 engine), forwards-compatible mode is activated.

Under this mode:

  1. Unknown top-level elements are ignored.
  2. Unknown instruction elements inside templates do not immediately trigger a fatal error if they contain an <xsl:fallback> child element.
  3. Combining forwards-compatible mode with element-available() allows developers to deliberately test capabilities and decide whether to structure logic via explicit conditionals or through nested <xsl:fallback> declarations.

Bridging Proprietary Extensions and Standards

Heterogeneous environments often feature differing proprietary element namespaces, such as EXSLT (http://exslt.org/common) versus processor-specific elements like saxon:iterate. The element-available() function acts as a discovery mechanism to detect which extension namespace is actively loaded:

<xsl:choose>
    <xsl:when test="element-available('exsl:document')">
        <exsl:document href="output.xml">
            <xsl:copy-of select="."/>
        </exsl:document>
    </xsl:when>
    <xsl:otherwise>
        <xsl:message terminate="no">Multiple output document creation is not supported by this engine.</xsl:message>
    </xsl:otherwise>
</xsl:choose>

By verifying that an extension element is recognized prior to execution, the stylesheet isolates processor-dependent behavior, ensuring consistent transformations across diverse production infrastructures.
