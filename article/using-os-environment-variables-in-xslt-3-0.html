Using OS Environment Variables in XSLT 3.0

This article provides an overview of how to retrieve and use operating system environment variables in XSLT 3.0 to manage runtime configurations. With the integration of XPath 3.0 and 3.1 functions into XSLT 3.0, developers can now read host system properties dynamically—such as deployment targets, paths, and system configurations—directly within stylesheets without requiring external wrapper scripts or explicit command-line parameter passing.

Native XPath 3.0 Environment Functions

XSLT 3.0 processors implement the XPath 3.0/3.1 F & O (Functions and Operators) specification, which introduces two primary functions within the standard fn namespace for interacting with the operating system environment:

  1. fn:environment-variable($name as xs:string) as xs:string?
    Returns the value of the specified system environment variable as a string. If the variable does not exist, it returns an empty sequence (()).

  2. fn:available-environment-variables() as xs:string*
    Returns a sequence of strings containing the names of all environment variables accessible to the transformation context.

Basic Syntax and Retrieval

You can access an environment variable anywhere an XPath expression is evaluated. The function can be called directly or with the standard Q{http://www.w3.org/2005/0xpath-functions} or fn: prefix.

<xsl:stylesheet xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
                xmlns:xs="http://www.w3.org/2001/XMLSchema"
                xmlns:fn="http://www.w3.org/2005/xpath-functions"
                version="3.0">

  <xsl:template match="/">
    <configuration>
      <app-env>
        <xsl:value-of select="fn:environment-variable('ENVIRONMENT_NAME')"/>
      </app-env>
    </configuration>
  </xsl:template>

</xsl:stylesheet>

Providing Fallback Defaults

Because fn:environment-variable returns an empty sequence when an environment variable is unset, you should supply fallback logic to ensure reliable execution. This can be handled using the empty() function or an XPath if-then-else expression:

<xsl:variable name="deployment-mode" as="xs:string"
  select="if (fn:environment-variable('DEPLOY_ENV')) 
          then fn:environment-variable('DEPLOY_ENV') 
          else 'development'"/>

Alternatively, you can use the comma sequence constructor paired with a subsequence check:

<xsl:variable name="base-path" as="xs:string"
  select="(fn:environment-variable('DATA_DIR'), '/default/data/path')[1]"/>

Combining Global Parameters with Environment Variables

A flexible architecture uses global xsl:param declarations that default to operating system variables. This pattern allows the host runtime environment to govern behavior by default, while still allowing callers to override values explicitly through transformation arguments:

<xsl:param name="output-directory" as="xs:string"
  select="(fn:environment-variable('OUTPUT_DIR'), '/tmp/output')[1]"/>

<xsl:param name="debug-mode" as="xs:boolean"
  select="fn:environment-variable('APP_DEBUG') = 'true'"/>

Validating Variable Availability

Before consuming dynamic variables, you can inspect whether the host environment has exposed them using fn:available-environment-variables():

<xsl:if test="'SECRET_KEY' = fn:available-environment-variables()">
  <!-- Perform actions dependent on variable existence -->
</xsl:if>

Processor Security Considerations

Operating system access is subject to processor-level security policies. In enterprise processors like Saxon (EE/PE), access to external environment variables may be sandboxed or disabled by default depending on the execution context.

To ensure your environment variables are readable:

  • Ensure the executing user account has read permissions for the targeted environment variables.
  • Verify that your XSLT processor does not have security restrictions enabled (such as Saxon’s FeatureKeys.ALLOW_EXTERNAL_FUNCTIONS set to false) that restrict access to system facilities.
