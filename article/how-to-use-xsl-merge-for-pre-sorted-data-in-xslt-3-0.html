How to Use xsl:merge for Pre-Sorted Data in XSLT 3.0

The xsl:merge instruction introduced in XSLT 3.0 provides a declarative mechanism to combine multiple data sources based on common key values without requiring all datasets to be loaded into memory at once. By declaring input sequences as pre-sorted, the XSLT processor can apply an efficient merge-sort algorithm across streams, processing items incrementally and in constant memory. This article explains the technical mechanics of xsl:merge, the roles of its child instructions, and how it handles pre-sorted input streams efficiently.

The Problem of Merging in Earlier XSLT Versions

In XSLT 1.0 and 2.0, combining records from two or more external documents typically required loading the full documents into tree structures, combining their nodes into a single sequence, and applying xsl:sort or xsl:for-each-group. For massive datasets, this approach often caused out-of-memory errors because processors had to buffer the entire collection of documents in memory before producing any output.

Architecture of xsl:merge

XSLT 3.0 solves this bottleneck by introducing a multi-way merge framework consisting of four core components:

  • <xsl:merge>: The parent element that orchestrates the merging process.
  • <xsl:merge-source>: Defines an individual input sequence, how to select its items, and whether the input is already sorted.
  • <xsl:merge-key>: Specifies the expression used to extract the comparison key for each item in a source.
  • <xsl:merge-action>: Contains the template logic evaluated for each unique key or group of matched items.

Leveraging Pre-Sorted Streams with sort-before-merge

The key attribute that enables streaming and prevents memory exhaustion when handling pre-sorted data is sort-before-merge="no" on <xsl:merge-source>.

By default, an XSLT processor might assume inputs must be sorted prior to merging (sort-before-merge="yes"), forcing it to read and sort the entirety of each stream. When set to sort-before-merge="no", the processor trusts that the input stream is already ordered according to the specified xsl:merge-key.

Because the data is guaranteed to be ordered, the processor maintains an internal cursor at the head of each stream. It only compares the current items across the inputs, selecting the lowest key (in ascending order) to advance. This reduces the time complexity to \(O(N)\) across all combined items and limits memory usage to \(O(K)\), where \(K\) is the number of open sources.

Practical Example

Consider combining an incremental transaction log with a master customer ledger where both files are already sorted ascending by customer-id:

<xsl:merge>
    <xsl:merge-source name="master" 
                      for-each-item="doc('customers.xml')/customers/customer" 
                      sort-before-merge="no">
        <xsl:merge-key select="@id" order="ascending" data-type="text"/>
    </xsl:merge-source>
    
    <xsl:merge-source name="transactions" 
                      for-each-item="doc('transactions.xml')/transactions/txn" 
                      sort-before-merge="no">
        <xsl:merge-key select="@customer-id" order="ascending" data-type="text"/>
    </xsl:merge-source>

    <xsl:merge-action>
        <customer-record id="{current-merge-key()}">
            <xsl:copy-of select="current-merge-group('master')"/>
            <transactions>
                <xsl:copy-of select="current-merge-group('transactions')"/>
            </transactions>
        </customer-record>
    </xsl:merge-action>
</xsl:merge>

Processing Current Items

Inside <xsl:merge-action>, specific context functions provide access to the items associated with the current key:

  • current-merge-key(): Returns the value of the key currently being processed.
  • current-merge-group(): Returns all items across all sources matching the current key.
  • current-merge-group('source-name'): Restricts the returned items to a specific named <xsl:merge-source>, allowing selective handling when a key exists in one source but not another (equivalent to outer joins).

If a pre-sorted stream violates the expected order during execution, an conformant processor detecting the mismatch raises a dynamic error (XTDE2230), guaranteeing data integrity throughout the merge operation.
