XSLT position() in Templates vs Filter Predicates

In XSLT, the position() function returns the 1-based index of the context node within the current context list, but its exact output depends heavily on where it is evaluated. This article breaks down the behavioral differences of position() when used inside template bodies (<xsl:template> and <xsl:for-each>) versus inside XPath filter predicates ([ ... ]), explaining how the evaluation context shifts and how to avoid common indexing mistakes.

Context in Template Bodies and xsl:for-each

When position() is called within the body of an <xsl:template> or an <xsl:for-each> block, it evaluates against the sequence of nodes selected for processing by <xsl:apply-templates> or <xsl:for-each>.

Key characteristics in this context include:

  • Iteration Order: The function returns the current step in the execution loop. If five <item> elements are selected, position() evaluates from 1 through 5 sequentially.
  • Impact of Sorting: If <xsl:sort> is used inside <xsl:apply-templates> or <xsl:for-each>, position() reflects the sorted order rather than the original document order. The first node processed after sorting returns 1, regardless of where it appeared in the source XML.
  • Scope: The context list is fixed before the templates execute. The last() function in this scope represents the total number of items selected by the driving instruction.

Context Inside XPath Filter Predicates

When position() is used inside a square-bracket predicate (such as //item[position() <= 3]), it operates on the immediate sequence generated by the step preceding the predicate.

Key characteristics in this context include:

  • Step-Local Evaluation: The predicate establishes an isolated context for each step in a path expression. In the expression //section/item[1], the predicate [1] evaluates against each <section>'s children separately, selecting the first <item> of each section rather than the first <item> in the entire document.
  • Document Order by Default: Standard XPath axis steps evaluate predicates in document order (or reverse document order for reverse axes like ancestor:: or preceding-sibling::), completely independent of any <xsl:sort> directives defined elsewhere.
  • Chained Predicates: Each predicate in a chain resets the context for the subsequent predicate. For example, in //item[position() > 2][position() = 1], the first predicate filters the sequence to items at position 3 and higher, and the second predicate selects the first item from that resulting sequence (which is the 3rd original item).

Summary of Differences

Feature Inside Template Body Inside Filter Predicate
Context List The node sequence passed to the template or loop The node sequence generated by the preceding XPath step
Sorting Respects <xsl:sort> transformations Ignores <xsl:sort>; follows axis traversal order
Primary Purpose Displaying counters, alternating row styles, or flow control Filtering which nodes are selected before template execution

Understanding this distinction ensures that numbering rules and node filters target the intended elements accurately. If you need to filter nodes based on their sorted order rather than document order, you must sort them into a temporary variable or iterate over them with <xsl:for-each> and test position() inside the body, rather than relying on a path predicate.
