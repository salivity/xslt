Feature Toggling with XSLT 3.0 Static Parameters

XSLT 3.0 introduces static parameters to enable conditional compilation and build-time configuration directly within stylesheets. By evaluating parameters during the stylesheet compilation phase rather than during transformation execution, developers can dynamically toggle features, adapt processing for specific environments, and eliminate unused code paths before transformation begins. This article explains how static parameters function, how they interface with compile-time expressions, and how to use them for effective feature management and environment configuration.

Understanding Static Parameters in XSLT 3.0

In standard XSLT workflows, parameters declared with <xsl:param> are dynamic. They are evaluated at runtime, meaning the stylesheet structure remains fixed while data values change.

XSLT 3.0 introduces the static="yes" attribute to <xsl:param>. A static parameter is evaluated strictly at compile time. Its value must be defined either by an expression containing only static sub-expressions (such as literals, calls to specific system functions, or references to other static parameters) or supplied externally by the invoking processor before compilation occurs.

<xsl:param name="ENABLE_BETA_FEATURES" as="xs:boolean" static="yes" select="false()"/>
<xsl:param name="ENVIRONMENT" as="xs:string" static="yes" select="'production'"/>

Because these values are resolved when the stylesheet is compiled into its executable form, the processor can make structural decisions about the stylesheet itself.

Compile-Time Evaluation with the use-when Attribute

Static parameters derive their primary utility through the use-when attribute. In XSLT 3.0, almost any element—whether an XSLT instruction, declaration, or literal result element—can include use-when.

The expression inside use-when is evaluated during compilation using static context. If the expression evaluates to true(), the element is retained; if it evaluates to false(), the XSLT processor strips the element from the stylesheet tree entirely.

<xsl:template match="record" use-when="$ENABLE_BETA_FEATURES">
    <!-- Advanced processing logic for beta testers -->
</xsl:template>

<xsl:template match="record" use-when="not($ENABLE_BETA_FEATURES)">
    <!-- Standard processing logic for production -->
</xsl:template>

When $ENABLE_BETA_FEATURES is set to false(), the beta template is not merely bypassed via runtime branching; it is completely omitted from the compiled stylesheet.

Implementing Feature Toggles

Feature toggling with static parameters allows teams to maintain a single stylesheet codebase while targeting different release stages or operational profiles.

Example: Development Logging and Diagnostic Output

<xsl:stylesheet xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
                xmlns:xs="http://www.w3.org/2001/XMLSchema"
                version="3.0">

    <xsl:param name="DEBUG_MODE" as="xs:boolean" static="yes" select="false()"/>

    <!-- Compile-time inclusion of diagnostic variables -->
    <xsl:variable name="build-timestamp" as="xs:dateTime" static="yes" 
                  select="current-dateTime()" use-when="$DEBUG_MODE"/>

    <xsl:template match="/">
        <output>
            <xsl:if test="true()" use-when="$DEBUG_MODE">
                <debug-info compiled-at="{$build-timestamp}"/>
            </xsl:if>
            <xsl:apply-templates/>
        </output>
    </xsl:template>

</xsl:stylesheet>

In production, $DEBUG_MODE compiles as false(). The <debug-info> element and the static $build-timestamp variable are fully discarded, avoiding unnecessary memory allocation and runtime condition checking.

Build-Time Configuration Workflows

Modern build pipelines (using tools like Ant, Maven, Gradle, or CLI tools for processors such as Saxon) pass static parameter values during compilation.

For example, when using the Saxon command-line interface, static parameters are passed with a leading question mark (?):

java -jar saxon-he-12.jar -s:source.xml -xsl:transform.xsl -o:output.xml ?ENABLE_BETA_FEATURES=true ?ENVIRONMENT=staging

This build-time mechanism supports several practical architectural requirements:

  • Dead-Code Elimination: Code belonging to disabled features is never compiled, reducing the memory footprint and startup overhead of compiled templates.
  • Targeting Processor Capabilities: Using use-when="system-property('xsl:supports-serialization') = 'yes'" alongside static parameters allows stylesheets to degrade gracefully across different processor editions.
  • Package and Dependency Management: The <xsl:use-package> and <xsl:import> elements also support use-when, allowing stylesheets to link entirely different modules, libraries, or vendor-specific extensions based on compile flags.
  • Code Security: Sensitive algorithms, development paths, or experimental routines can be excluded from production deployments, preventing reverse-engineering or accidental execution in production pipelines.
