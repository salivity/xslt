XSLT use-when Attribute for Conditional Inclusion

The use-when attribute in XSLT 2.0 and later versions provides compile-time conditional inclusion of stylesheet elements, enabling developers to selectively include or exclude code before the transformation executes. This feature ensures backward and forward compatibility, controls debugging routines, and handles processor-specific capabilities without causing static compilation errors. By evaluating expressions statically, use-when gives developers granular control over the stylesheet structure before any source document data is processed.

The Purpose of use-when

In standard XSLT processing, conditional instructions like <xsl:if> and <xsl:choose> operate dynamically at runtime based on the contents of the source XML document or runtime parameters. However, if a stylesheet contains instructions, functions, or schema components not supported by the XSLT processor compiling the sheet, the transformation halts with a static compilation error—even if the unsupported instruction is inside a branch of an <xsl:if> that would never execute.

The use-when attribute solves this limitation by allowing static preprocessing. Can be attached to any XSLT element, use-when contains an XPath expression that is evaluated at compile time. If the expression evaluates to true(), the element and its content are included in the compiled stylesheet. If it evaluates to false(), the element is stripped entirely from the stylesheet tree prior to compilation, ensuring that unsupported syntax or definitions do not trigger static errors.

Static Evaluation Context

Because use-when runs during the compilation phase, it operates in a restricted "static context." The XPath expression inside a use-when attribute cannot reference:

  • Context nodes, axes, or data from the input XML document.
  • Standard runtime variables or parameters (<xsl:param>, <xsl:variable>).
  • Runtime functions that depend on dynamic context (such as position() or last()).

Instead, use-when expressions can only use static information, which includes:

  • Core XPath functions that do not depend on the dynamic context (e.g., true(), false(), not()).
  • The system-property() function, used to inspect vendor, engine, and version data.
  • The function-available() and element-available() functions to check for processor capabilities.
  • Static variables and parameters declared with static="yes" (introduced in XSLT 3.0).

Primary Use Cases

1. Cross-Version and Multi-Engine Compatibility

A single stylesheet can serve multiple XSLT specifications (e.g., XSLT 2.0 and XSLT 3.0) or different vendor implementations (e.g., Saxon vs. Altova). By testing system properties or function availability, newer features can be isolated:

<xsl:include href="xslt3-transforms.xsl" 
             use-when="system-property('xsl:version') >= 3.0"/>

<xsl:include href="xslt2-transforms.xsl" 
             use-when="system-property('xsl:version') &lt; 3.0"/>

2. Eliminating Static Compilation Errors

If a stylesheet uses an extension function or an advanced feature like streaming or schema awareness, processors lacking that feature fail immediately upon compilation. Using use-when="function-available('custom:fast-parse')" ensures that code utilizing the extension is only compiled if the engine actually supports it.

3. Build-Time Configuration and Debugging

Developers can toggle modes such as verbose logging, development traces, or production optimizations. In XSLT 3.0, static parameters can be supplied at compile time:

<xsl:param name="DEBUG" select="false()" static="yes"/>

<xsl:template match="*" use-when="$DEBUG">
    <xsl:message>Processing node: <xsl:value-of select="name()"/></xsl:message>
    <xsl:next-match/>
</xsl:template>

When $DEBUG is set to false(), the diagnostic template is eliminated entirely, removing any runtime overhead or unwanted logging.
