Asynchronous XSLT With ixsl:schedule-action in SaxonJS

This article provides an overview of the ixsl:schedule-action extension instruction in SaxonJS, explaining how it enables asynchronous XSLT 3.0 execution in web browsers. By delegating tasks to the JavaScript event loop, ixsl:schedule-action allows developers to fetch remote data, introduce timed delays, and perform background processing without freezing the browser's user interface.

The Need for Asynchronous Processing in SaxonJS

Standard XSLT is a functional, synchronous language. When running in a web browser via SaxonJS, standard transformations execute on the main JavaScript UI thread. If a stylesheet attempts to fetch large external datasets or execute computationally expensive routines synchronously, the browser becomes unresponsive, leading to a degraded user experience.

The ixsl:schedule-action instruction, part of the Interactive XSLT (iXSLT) extension library (xmlns:ixsl="http://saxonica.com/ns/interactiveXSLT"), resolves this limitation. It allows SaxonJS to defer operations, effectively bridging the gap between XSLT execution and modern asynchronous web platform APIs.

Core Roles and Capabilities

The primary role of ixsl:schedule-action is to schedule a task to run after an asynchronous event completes or after a defined time interval. Instead of blocking thread execution, SaxonJS yields control back to the browser's event loop and resumes the enclosed instructions once the specified condition is met.

1. Asynchronous HTTP Requests

The instruction is widely used to initiate non-blocking network requests for XML, JSON, HTML, or plain text resources. By using the http-request attribute, developers pass an HTTP request map (or supply child ixsl:http-request configurations) to retrieve resources:

<ixsl:schedule-action http-request="$request-map">
    <xsl:call-template name="handle-response"/>
</ixsl:schedule-action>

When the network response is received, the instructions inside ixsl:schedule-action are invoked, and the response data becomes available through the ixsl:event() or ixsl:http-response() functions without having stalled the DOM during the transfer.

2. Timers and Delays

Using the wait attribute, ixsl:schedule-action functions similarly to JavaScript's setTimeout. It pauses execution for a specified number of milliseconds before evaluating its child sequence constructor:

<ixsl:schedule-action wait="500">
    <ixsl:set-property name="className" select="'fade-in'" object="id('status-box')"/>
</ixsl:schedule-action>

This capability is essential for managing user-feedback transitions, polling endpoints at regular intervals, throttling input events, and pacing DOM mutations.

3. Asynchronous Document Loading

SaxonJS supports asynchronous fetching and parsing of documents via the document attribute. Rather than halting the transform using the standard synchronous doc() function, ixsl:schedule-action document="data.xml" loads the target document in the background and evaluates its inner template once parsing is complete.

Execution Context and State Management

When ixsl:schedule-action executes, SaxonJS captures the current dynamic context—such as local variables and the context item—so that they remain accessible when the callback executes.

Key behavioral details include:

  • Non-Blocking Flow: Any XSLT instructions immediately following the ixsl:schedule-action element continue to evaluate without waiting for the scheduled action to resolve.
  • Result Tree Isolation: The instructions contained inside the ixsl:schedule-action do not contribute directly to the primary result tree of the invoking template. Instead, they interact with the application state via side-effect instructions, such as DOM updates (ixsl:set-property, xsl:result-document), or by triggering secondary templates.

Summary

In SaxonJS, ixsl:schedule-action acts as the fundamental boundary between declarative XSLT logic and the asynchronous JavaScript execution model. It allows applications to perform network I/O, handle timed events, and parse dynamic data while maintaining fluid, responsive user interfaces.
