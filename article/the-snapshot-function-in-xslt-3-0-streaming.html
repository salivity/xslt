The snapshot() Function in XSLT 3.0 Streaming

The snapshot() function in XSLT 3.0 enables developers to capture an in-memory, fully navigable representation of a subtree while processing an XML document in streaming mode. In streamed transformations, nodes are read sequentially, preventing backward navigation and multi-pass operations. Calling snapshot() on a streamed node bridges this gap by decoupling the selected node and its descendants from the strict forward-only pipeline, restoring full XPath navigation capabilities without consuming the memory required to load the entire document.

The Challenge of Streaming in XSLT 3.0

Streaming in XSLT 3.0 is designed to process XML documents too large to fit into available memory. To achieve this, the XSLT processor reads the input sequentially and discards elements once passed. As a result, streamed nodes are subject to severe restrictions:

  • Forward-only traversal: You cannot use reverse axes such as ancestor::, preceding::, or parent::.
  • Single-pass consumption: You cannot iterate over the same set of child nodes more than once.
  • Restricted XPath functions: Operations requiring random access, sorting, or lookahead cannot be executed directly on streamed nodes.

When complex transformation logic requires arbitrary navigation within a specific section of a large document, streaming rules often reject the stylesheet as non-streamable.

How snapshot() Solves the Problem

The snapshot() function creates a deep copy of a targeted streamed node and its entire subtree, loading that specific segment into memory. Once a node is captured via snapshot(), all standard non-streamed operations become valid for that fragment.

Key behaviors of snapshot() include:

  1. Full Axis Availability: Within the captured subtree, you can freely use child, descendant, following-sibling, and preceding-sibling axes.
  2. Multiple Traversals: The captured nodes can be queried, sorted, and processed multiple times.
  3. Preservation of Ancestor Context: Unlike standard tree detachment, snapshot() retains structural context by creating shallow copies of all ancestor elements up to the document root, including their attributes and namespace declarations.

snapshot() vs. copy-of()

While copy-of() can also materialize a streamed node into memory, snapshot() provides distinct advantages regarding document context:

  • copy-of() creates a detached document fragment rooted at the selected element. Any information located on ancestor elements—such as xml:lang, xml:base, or custom inherited metadata attributes—is lost.
  • snapshot() retains the ancestor chain. While the ancestors do not contain their other non-ancestor children (siblings to the current path), their presence allows expressions such as ancestor::department/@id or f:is-in-scope() to function correctly.

Practical Application

Consider a scenario where a multi-gigabyte log or catalog file must be transformed:

<xsl:mode streamable="yes" on-no-match="shallow-skip"/>

<xsl:template match="record">
    <xsl:variable name="rec" select="snapshot(.)"/>
    <!-- Full XPath is now legal on $rec -->
    <output-item id="{$rec/@id}" parent-type="{$rec/ancestor::batch/@type}">
        <xsl:for-each select="$rec/entry">
            <xsl:sort select="@timestamp" order="descending"/>
            <entry val="{@val}"/>
        </xsl:for-each>
    </output-item>
</xsl:template>

In this example, the processor streams the root and only keeps individual <record> elements in memory one at a time. The sorting operation and the reference to ancestor::batch/@type would cause a static analysis failure in pure streaming, but wrapping the node in snapshot() makes the template conform to streamability rules.

Performance Considerations

Because snapshot() allocates memory for the selected node, its descendants, and copies of its ancestors, it should be applied to relatively small, granular subtrees rather than broad container elements. Once the template finishes executing and references to the captured fragment go out of scope, the memory is reclaimed by the runtime garbage collector, maintaining a flat and predictable memory footprint throughout the transformation.
