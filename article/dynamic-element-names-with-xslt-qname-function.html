Dynamic Element Names with XSLT QName Function

This article explains how the XPath and XSLT QName() constructor dynamically instantiates qualified XML element names at runtime. By combining a namespace URI with a lexical QName (a prefix and local name), this function enables stylesheets to generate elements whose identities are determined programmatically from source data, parameters, or external configurations rather than being hardcoded into the transformation template.

The Role of fn:QName() in XSLT

In standard XSLT transformations, element names and namespaces are often static or evaluated using attribute value templates in the <xsl:element> instruction. However, when working with complex XML pipelines, schemas, or dynamic vocabularies, an XSLT processor needs a reliable, atomic representation of an element identity.

The fn:QName($paramURI as xs:string?, $paramQName as xs:string) as xs:QName function serves this purpose. Available in XPath 2.0 and XSLT 2.0 and later, it constructs an instance of the xs:QName data type directly from arbitrary string values during execution.

Function Signature and Parameters

The QName() constructor takes two parameters:

  1. Namespace URI ($paramURI): An optional string representing the target namespace. If passed as an empty sequence or zero-length string, the resulting QName resides in no namespace.
  2. Lexical QName ($paramQName): A required string consisting either of a single NCName (the local element name) or a prefix and local name separated by a colon (prefix:localName).

If a prefix is supplied in $paramQName, the $paramURI cannot be empty, as a prefix must always be mapped to an explicit URI according to XML namespace specifications.

The Dynamic Instantiation Process

When the XSLT processor evaluates QName(), it performs the following operational steps:

  1. Lexical Validation: The processor validates the $paramQName string to ensure that both the prefix (if present) and the local part conform to the syntactic rules of an NCName (Non-Colonized Name). If invalid characters are detected, a dynamic error is thrown.
  2. Namespace Binding: Unlike resolve-QName(), which looks up prefixes in the static in-scope namespace context of the stylesheet, QName() explicitly binds the supplied prefix to the URI provided in $paramURI. This allows the creation of prefix-to-URI associations that do not exist statically within the stylesheet itself.
  3. Atomic Instantiation: The processor outputs an xs:QName item containing three distinct components: the local name, the namespace URI, and the optional prefix.

Applying Dynamically Created QNames

Once instantiated, dynamic QNames can be utilized across several XSLT constructs:

  • Generating Dynamic Elements: In XSLT 2.0+, elements are typically created using <xsl:element>. By extracting the local name and prefix via local-name-from-QName() and prefix-from-QName(), or passing the raw variables into the name and namespace attributes, the processor constructs the output element tree dynamically:
<xsl:variable name="dynamicQName" select="QName('https://example.com/ns', 'custom:DynamicNode')" />

<xsl:element name="{local-name-from-QName($dynamicQName)}" 
             namespace="{namespace-uri-from-QName($dynamicQName)}">
    <xsl:value-of select="'Dynamic content'" />
</xsl:element>
  • Introspection and Dynamic Matching: Dynamic QNames can be compared against the node-name() of incoming source nodes. This allows stylesheets to match and transform nodes whose definitions vary at runtime without requiring static matching templates for every possible namespace combination.
  • XSLT 3.0 Node Constructors: In modern functional transformations or XQuery-adjacent patterns, xs:QName instances can be supplied directly to node-generation functions and dynamic function calls to generate fully qualified elements on the fly.
