Enforcing Strict Inputs in XSLT with exact-single

This article explores how applying the exact-single() pattern during sequence checking guarantees that XSLT transformations receive precisely one item, neither more nor less. By examining sequence cardinality, type definitions, and runtime validation, you will learn how this pattern catches malformed inputs early, prevents silent downstream data corruption, and enforces rigorous structural contracts across stylesheets.

In XSLT and XPath, virtually all values are handled as sequences. A query designed to locate a specific node or calculate a value can return an empty sequence (), an individual item, or a sequence of multiple items. This flexibility introduces subtle bugs when a template, function, or variable assumes it is operating on a single scalar value or individual element. Without explicit constraints, passing an empty sequence might cause a template to quietly skip execution, while passing multiple items might inadvertently bind only the first item or trigger unhandled type errors far from the root cause.

The exact-single() pattern addresses this issue by strictly validating that a target sequence has a cardinality of exactly one (\(N = 1\)). In standard XSLT and XPath implementations, this pattern is represented either through the standard function fn:exactly-one(), a custom validation function named exact-single(), or strict type signatures omitting sequence indicators (such as as="xs:string" or as="element(Order)" rather than using *, +, or ?).

When applied, the pattern enforces data integrity through two distinct boundary checks:

  1. Rejection of Empty Sequences: If the source data does not contain the required node or value, the pattern refuses to evaluate further. Instead of propagating an empty sequence through your transformation pipeline—which often produces empty output tags or missing attributes—the processor immediately raises a dynamic error (such as FORG0005 when using fn:exactly-one()).

  2. Rejection of Multiple Matches: If an input document contains duplicate elements where only one is permitted, standard queries without cardinality checks might mask the anomaly. The exact-single() pattern detects that the sequence count exceeds one and halts execution immediately. This prevents the stylesheet from arbitrarily selecting the first node or producing malformed target structures.

Consider a practical scenario involving an order-processing stylesheet. If a template requires a customer ID, defining the parameter as <xsl:param name="customerId" as="xs:string"/> or checking the sequence using an assertion like exact-single($node/CustomerID) creates an uncompromising contract. If the input document contains two <CustomerID> tags or omits the tag entirely, the transformation fails at the input boundary.

Employing the exact-single() pattern eliminates non-deterministic behavior in XSLT. By shifting error discovery from output inspection to input ingestion, transformations become self-validating, maintainable, and resilient against unexpected schema variations.
