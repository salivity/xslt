Using codepoints-to-string for Entities in XSLT

In XSLT development, generating specific symbols, control characters, or non-standard character entities can lead to serialization conflicts or XML parsing errors. The XPath function codepoints-to-string() solves this issue by converting Unicode code point integers into their corresponding string characters directly in the transformation pipeline. This article explains the role of codepoints-to-string() in handling specialized character output, avoiding entity declaration overhead, and maintaining clean encoding standards across XML and text outputs.

What is codepoints-to-string()?

Introduced in XPath 2.0 and natively supported in XSLT 2.0 and later, codepoints-to-string() is a built-in function with the following signature:

fn:codepoints-to-string($arg as xs:integer*) as xs:string

It takes one or more Unicode code point values represented as decimal integers and outputs a string composed of the characters identified by those code points.

The Challenge with Non-Standard Character Entities

Standard XML recognizes only five predefined entity references: &amp;, &lt;, &gt;, &quot;, and &apos;. When transforming XML documents, handling characters outside standard character sets presents multiple challenges:

  1. Parser Validation Errors: Trying to output non-standard named entities (like &customChar;) without an explicit DTD declaration causes XML parsers to throw fatal errors.
  2. Encoding Conflicts: Hardcoding raw characters in the stylesheet can cause corruption if files are saved, transmitted, or interpreted across incompatible encodings (such as UTF-8 versus ISO-8859-1).
  3. Dynamic Character Generation: When character representations arrive as numeric data (such as Unicode hex or decimal values from an external database), standard text nodes cannot dynamically interpret them as characters without programmatic conversion.

The Purpose of codepoints-to-string() in XSLT

Using codepoints-to-string() resolves these issues by handling character generation at the data model level rather than relying on textual entity parsing.

1. Dynamic Unicode Resolution

When input data contains numeric Unicode identifiers, codepoints-to-string() converts these numbers directly into characters without needing complex string manipulation or lookup tables:

<!-- Outputs the Euro symbol (€) using decimal code point 8364 -->
<xsl:value-of select="codepoints-to-string(8364)"/>

2. Safe Injection of Reserved or Special Characters

When outputting plain text, CSVs, or proprietary legacy formats, developers frequently need to insert non-printable control characters (such as line feeds, tabs, or ASCII separators). codepoints-to-string() inserts these cleanly without modifying XML whitespace rules:

<!-- Inserts a horizontal tab (code point 9) -->
<xsl:value-of select="codepoints-to-string(9)"/>

3. Working with Character Maps for Named Entities

If the final serialized output must contain literal non-standard entities (such as outputting legacy HTML or custom SGML containing &specialEntity;), codepoints-to-string() pairs with XSLT's <xsl:character-map>:

<xsl:character-map name="custom-entities">
    <xsl:output-character character="&#xE001;" string="&amp;customChar;"/>
</xsl:character-map>

<xsl:output method="xml" use-character-maps="custom-entities"/>

<xsl:template match="/">
    <!-- Dynamically outputs the mapped entity reference &customChar; -->
    <xsl:value-of select="codepoints-to-string(57345)"/>
</xsl:template>

In this pattern, the processor safely holds the character as a valid Unicode point internally (in the Private Use Area at 57345 / 0xE001) during processing, only expanding it into the literal entity string at serialization time.

Key Advantages

  • Encoding Independence: Because characters are identified by numeric code points, stylesheets remain safe against accidental text encoding conversions during deployment.
  • No DTD Dependency: Eliminates the need to declare custom entity lists inside Document Type Definitions just to output specific symbols.
  • Precision and Validation: The function immediately fails if provided an invalid XML character code point (such as surrogate code points or values out of Unicode range), catching character errors early during transformation.
