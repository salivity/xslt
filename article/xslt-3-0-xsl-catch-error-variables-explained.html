XSLT 3.0 xsl:catch Error Variables Explained

In XSLT 3.0, the <xsl:try> and <xsl:catch> instructions allow developers to trap runtime dynamic errors and gracefully recover or log failures. When an error is caught within an <xsl:catch> block, the processor automatically populates several implicit variables within the standard error namespace (http://www.w3.org/2005/xqt-errors, bound by default to the err prefix). This guide explains the exact purpose, data type, and diagnostic information provided by the three primary variables: err:code, err:description, and err:value.

err:code

The err:code variable holds an xs:QName identifying the specific error that triggered the catch block.

  • Standard Errors: If the error was raised by the XSLT processor or standard XPath functions (such as a type error, division by zero, or failure to parse a document), err:code contains a standardized error code defined by the W3C specification (for example, err:FOAR0001 for division by zero).
  • User-Defined Errors: When an error is raised explicitly using the fn:error() function, err:code contains the QName supplied in the function call. If fn:error() is called without arguments, err:code defaults to err:FOER0000.

Because err:code is an xs:QName, you can perform conditional logic using functions such as local-name-from-QName() or evaluate against specific namespace URIs.

err:description

The err:description variable is an xs:string providing human-readable details about the failure.

  • Processor Messages: For standard system errors, this variable contains implementation-dependent text generated by the XSLT processor explaining what went wrong (e.g., "Cannot divide by zero" or "Failed to parse external document").
  • Custom Messages: When using fn:error(), the second argument (if supplied) maps directly to err:description.

This variable is primarily used for logging, diagnostics, or constructing fallback XML reports for end users.

err:value

The err:value variable contains an arbitrary sequence (item()*) representing the application data or error object associated with the exception.

  • Processor Errors: For native runtime errors generated by the processor, err:value is typically an empty sequence.
  • Custom Error Data: When an error is triggered programmatically using fn:error($code, $description, $error-object), the third argument ($error-object) is assigned to err:value.

This variable enables advanced error handling by allowing you to pass structured diagnostic data—such as invalid XML elements, serialized request payloads, or status code maps—directly into the catch block for programmatic recovery.

Usage Example

<xsl:try>
    <!-- Risky operation or custom error -->
    <xsl:sequence select="fn:error(xs:QName('local:PAYMENT_FAILED'), 'Transaction declined', map { 'retry': false() })"/>
    <xsl:catch>
        <error-report>
            <code local="{local-name-from-QName($err:code)}" uri="{namespace-uri-from-QName($err:code)}"/>
            <message><xsl:value-of select="$err:description"/></message>
            <has-data><xsl:value-of select="exists($err:value)"/></has-data>
        </error-report>
    </xsl:catch>
</xsl:try>
