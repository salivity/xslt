Character Analysis with XSLT string-to-codepoints

This article explores how the XPath and XSLT function string-to-codepoints() facilitates low-level character analysis in modern XML processing pipelines. By converting abstract text strings into sequences of discrete Unicode integer code points, XSLT developers gain the ability to inspect, filter, and sanitize text at the individual byte and glyph level. This technique resolves issues that standard high-level string manipulation functions and regular expressions often struggle to address.

How string-to-codepoints() Works

Introduced in XPath and XSLT 2.0 and carried through XSLT 3.0, fn:string-to-codepoints($arg as xs:string?) as xs:integer* takes an input string and converts it into a sequence of zero or more integers. Each returned integer represents the unique Unicode scalar value (code point) assigned to each character in the string.

For example, evaluating string-to-codepoints('XML') yields the sequence (88, 77, 76). If the input is an empty string or an empty sequence, the function returns an empty sequence.

Detecting Invisible and Control Characters

High-level functions like contains(), starts-with(), or standard regex-based replacements can obscure non-printable or invisible characters. These include zero-width spaces (&#x200B; / 8203), byte order marks (&#xFEFF; / 65279), and legacy ASCII control characters (values 0 through 31).

By converting text to integers, developers can run direct numerical comparisons to identify and strip problematic characters:

<xsl:variable name="codepoints" select="string-to-codepoints(.)"/>
<xsl:variable name="has-control-chars" select="some $cp in $codepoints satisfies ($cp lt 32 and not($cp = (9, 10, 13)))"/>

This logic evaluates whether a string contains any invalid XML control characters without relying on fragile string-matching techniques.

Range-Based Unicode Validation

Text verification often requires ensuring that input data belongs to specific scripts, such as standard ASCII, Basic Latin, or extended alphabets. string-to-codepoints() enables range-based arithmetic validation across Unicode blocks:

  • Basic ASCII Validation: Checking if every code point is less than or equal to 127 (every $cp in string-to-codepoints($input) satisfies $cp le 127).
  • Non-BMP / Surrogate Character Detection: Identifying characters residing outside the Basic Multilingual Plane (code points greater than 65535, such as modern emojis or rare historical scripts).

This approach provides a reliable way to enforce legacy encoding limits (such as Latin-1 or ASCII-only requirements) before data is serialized or forwarded to downstream systems.

Reconstructing Strings with codepoints-to-string()

Low-level analysis frequently concludes with transformation or cleanup. The companion function fn:codepoints-to-string($arg as xs:integer*) as xs:string takes a sequence of integers and reconstructs a valid string.

Together, these functions allow you to filter text dynamically using sequence expressions:

<xsl:variable name="clean-text" select="codepoints-to-string(string-to-codepoints(.)[. >= 32])"/>

This pattern strips out all characters below Unicode 32 in a single step, giving you fine-grained control over character streams directly within XSLT stylesheets.
