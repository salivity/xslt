JSON to XML via XSLT: Key-Value Record Pattern

The key-value record pattern in XSLT is a structural design strategy used to transform dynamic, heterogeneous, or deeply nested JSON objects into a predictable and standardized XML format. When converting JSON to XML, mapping arbitrary object keys directly to XML element names often introduces schema instability, invalid element names, and complex querying requirements. The key-value pattern resolves these issues by abstracting variable keys into uniform XML attributes or child elements, ensuring that the resulting document adheres to strict XML schemas and remains easily queryable via XPath.

Overcoming XML Element Naming Constraints

JSON allows nearly any valid string to be used as an object key, including strings containing whitespace, special characters, punctuation, or leading numeric digits (such as "123_id" or "first name"). Conversely, the W3C XML specification enforces strict rules for element tag names, which cannot start with numbers, cannot contain spaces, and restrict most punctuation.

Attempting to map such JSON keys directly to XML elements causes transformation errors or generates non-well-formed XML. The key-value record pattern bypasses this limitation by mapping the JSON key to a standard XML element's value or attribute:

<!-- Avoids invalid tags like <123_id> or <first name> -->
<entry key="123_id">Value</entry>
<entry key="first name">Value</entry>

Enabling Predictable Schema Validation (XSD)

In systems requiring strict data contracts, XML Schemas (XSD) define the allowed structure, types, and element names. When JSON objects use keys dynamically—such as using user IDs, timestamps, or product codes as keys—a direct conversion would generate an infinite set of potential element names, breaking static schema validation.

The key-value pattern normalizes open-ended JSON maps into a predictable, repeating model:

<record>
  <key>dynamic_identifier</key>
  <value>payload</value>
</record>

This predictable structure allows developers to write precise XSD schemas using simple repeating elements (<xs:sequence> with maxOccurs="unbounded") without relying on lax validation, wildcards, or xs:any definitions.

Simplifying Downstream XPath Queries

Directly translating variable JSON keys into element names forces downstream consumers to use dynamic or complex XPath expressions. If the element name itself carries data (e.g., <user_9876>), finding all users requires pattern matching against node names using functions like name() or local-name().

By standardizing the structure into key-value records, downstream systems can execute clean, indexable, and performant XPath queries:

//record[key = 'user_9876']/value

This decouples the structural schema from the data values, making downstream code easier to read, optimize, and maintain.

Aligning with W3C XSLT 3.0 Standards

Modern XSLT implementations leverage the standard XPath and XSLT 3.0 function fn:json-to-xml(). The W3C specification for this function natively implements the key-value record concept. Instead of generating arbitrary element names, fn:json-to-xml() represents JSON maps using standard elements (<map>, <string>, <number>, <array>) and stores the original JSON property name in a @key attribute:

<map xmlns="http://www.w3.org/2005/0xpath-functions">
  <string key="user_123">John Doe</string>
</map>

Using the key-value record pattern in custom XSLT templates ensures architectural consistency with the W3C standard processing model, making templates portable across various XSLT processors like Saxon or BaseX.

Handling Dictionaries vs. Static Objects

In JSON, objects serve two distinct semantic purposes:

  1. Fixed entities: Modeled like classes or structs, where keys are known schema properties (e.g., firstName, lastName).
  2. Associative arrays (Dictionaries): Collections of items where keys represent data lookups rather than structural categories.

The key-value record pattern explicitly signals that the JSON object is an associative array. Applying this pattern in XSLT ensures that data contained within keys is preserved as queryable text rather than mistakenly elevated to structural metadata.
